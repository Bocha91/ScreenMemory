# ScreenMemory

Утилита для Windows 10, которая сохраняет и восстанавливает раскладку окон по виртуальным
рабочим столам: какие окна открыты, на каком десктопе, в каких координатах и размерах.
При восстановлении окна расставляются по местам, а приложения, окон которых нет, —
запускаются (кроме консолей: что было запущено внутри, из слепка неизвестно — такие окна
попадают в `bin\admin.log`).

```
ScreenMemory.exe save                 сохранить текущую раскладку в bin\layout.txt
ScreenMemory.exe restore              восстановить раскладку из bin\layout.txt
ScreenMemory.exe restore --dry-run    показать план восстановления, ничего не меняя
ScreenMemory.exe AutoSave             поставить в Планировщик сохранение каждые N минут
ScreenMemory.exe AutoRestore          поставить в Планировщик восстановление при входе в систему
ScreenMemory.exe Uninstall            снять задачи AutoSave/AutoRestore и автозагрузку
ScreenMemory.exe --list               показать десктопы, pinned-приложения и окна
```

`save`/`restore` работают от обычного пользователя, `AutoSave`/`AutoRestore`/`Uninstall`
нужны права администратора (без них — сообщение и код возврата 5). За запуск — ровно одна
команда: `save restore`, `AutoSave restore`, `--list --version` — ошибка разбора (код 64).

Ограничения и решения описаны в `PLAN.md`, история решений — в `CONTEXT.md`.

## Сборка

Требуется Visual Studio 2019 (или новее) с инструментами C++ x64. `cl.exe` в PATH не нужен —
`build.bat` сам находит и вызывает `vcvars64.bat`.

```
build.bat        собирает bin\ScreenMemory.exe (объектники — в T:\ScreenMemory\obj)
clean.bat        удаляет exe и объектники
```

Первый запуск `build.bat` дополнительно генерирует иконки `bin\save.ico` и `bin\restore.ico`
через `tools\make_icons.ps1` (System.Drawing, ничего устанавливать не нужно).

Проверки после сборки:

```
tests\smoke.bat                                    контракт командной строки и коды возврата
powershell -File tools\check_exe.ps1               иконки и манифест внутри exe
powershell -File tools\check_task_xml.ps1          XML задач AutoSave/AutoRestore
powershell -File tools\check_task_xml.ps1 -Register  то же + регистрация задачи в Планировщике
```

## Файлы

```
bin\ScreenMemory.exe                  сама программа
bin\layout.txt                        текущий слепок раскладки
bin\layout-YYYY-MM-DD_HH-MM-SS.txt    до 5 предыдущих слепков (ротация)
bin\admin.log                         журнал последнего запуска restore: консоли и окна админ-приложений (перезаписывается)
bin\Config.ini                        настройки: программа мониторов, интервал AutoSave, задержка AutoRestore (файл необязателен)
bin\save.ico, bin\restore.ico         иконки для ярлыков (они же вшиты в exe)
T:\ScreenMemory\screenmemory.log      подробный лог (ключ --verbose); если диска T: нет — рядом с exe
```

## Настройки: `Config.ini`

Рядом с exe может лежать `Config.ini`. Файл необязателен: нет его — работают значения
по умолчанию. В нём — предварительная программа для `restore` и параметры автозапуска:

```
prelaunch=C:\...\MultiMonitorTool.exe   программа, которую надо запустить перед restore
prelaunch-args=                         её аргументы командной строки (обычно не нужны)
prelaunch-timeout=0                     сколько секунд ждать закрытия её окна; 0 — без ограничения
AutoSave=10                             интервал задачи AutoSave, минуты (1…1440)
AutoRestoreDelay=30                     задержка задачи AutoRestore после входа, секунды (0…3600)
```

Зачем: второй монитор-телевизор включается позже компьютера, и рабочий стол на него не
приходит, пока это не поправит сторонняя утилита. Если `prelaunch` задан, `restore` сначала
запускает эту программу и ждёт, пока вы не закроете её окно, — и только потом восстанавливает
раскладку:

```
> bin\ScreenMemory.exe restore
ScreenMemory 0.8.5
каталог: E:\PCAD\ScreenMemory\bin

Предварительная программа: C:\с рабочего стола\My Util\multimonitortool-x64\MultiMonitorTool.exe
  закройте её окно — после этого работа продолжится
  программа закрыта (ждали 6.4 с), работаю дальше

Применено: 61, перенесено на другой десктоп: 12, z-order выставлен: 61
```

Для `save` предварительный шаг не выполняется: он ничего не восстанавливает, а только
записывает то, что видно сейчас.

Если программы нет, она не запускается или окно не закрыли за `prelaunch-timeout` секунд,
печатается предупреждение, и восстановление продолжается без неё. `--dry-run` и `--list`
предварительный шаг тоже не выполняют: они ничего не меняют.

`AutoSave` и `AutoRestoreDelay` нужны только командам `AutoSave`/`AutoRestore`: они читаются
в момент создания задачи, поэтому после правки `Config.ini` команду надо выполнить снова —
задача перезапишется новыми параметрами (об этом же пишет сам `AutoSave`).

Формат файла: `ключ=значение`, по строке на ключ; `;` и `#` в начале строки — комментарий;
секции `[...]` допускаются; значения можно писать в кавычках и с переменными среды
(`%USERPROFILE%`). Кодировка — UTF-8 (Блокнот сохраняет её сам) или UTF-16. Незнакомые ключи
не мешают: в `--verbose` они попадают в лог, поэтому в файл можно добавлять свои пометки и
заготовки будущих настроек.

## Проверка окружения: `ScreenMemory.exe --list`

Ключ ничего не сохраняет и не меняет — печатает то, что программа видит прямо сейчас:
виртуальные рабочие столы (индекс, GUID, имя, пометка «текущий»), приложения, помеченные
«показывать на всех рабочих столах» (pinned), и окна всех этих столов.

```
Виртуальные десктопы: 4 (источник: реестр, VirtualDesktopIDs)
текущий десктоп: [2] «Game» (по: окно в фокусе)
  [0] {3BBD80D8-D12B-4B44-AC94-2579E6984975}  «Работа»
  [1] {09D112DA-0BB6-4073-8A33-63EFF448696E}  «AliExpress»
  [2] {D7B24E7A-F0FF-435E-BA53-55D2EFDC7A32}  «Game»   <= текущий
  [3] {4AD61A74-9B8C-4F97-AFC3-C09DDC97FF33}  «ESP32»

Pinned-приложения (показывать на всех рабочих столах): 9
  путь   C:\с рабочего стола\My Util\Telegram_portable.1.9.9\Telegram.exe
  AUMID  Microsoft.VisualStudioCode
  папка  C:\Program Files\OpenConnect-GUI\openconnect-gui.exe
```

Что проверить глазами: число и порядок десктопов должны совпадать с Task View,
а список pinned — с контекстным меню «Показывать это окно на всех рабочих столах».
Имена читаются из реестра, поэтому после переименования десктопа `--list` сразу показывает новое имя.

Совсем стереть имя в Windows нельзя: если очистить поле в Task View, вернётся прежнее имя.
Поэтому де-факто безымянным бывает либо десктоп, которому имя не задавали ни разу, либо
десктоп, которому вручную дали имя из одного пробела. И то и другое `--list` печатает как
`(без имени)`; нормализация только при выводе — в реестре и в файле раскладки имя остаётся
как есть.

### Окна в `--list`

Окна печатаются сгруппированными по десктопу и в порядке z-order (сверху вниз):

```
Окна: кандидатов 60 из 836 верхнеуровневых; cloaked: shell 32 (другие десктопы), app 0
  shell — окно на другом виртуальном столе (в слепок попадает), app — окно спрятало приложение (UWP suspended)
  exe прочитан у 60, AUMID — у 16, папка Проводника — у 34

  [0] «Работа»   <= текущий — окон 23
     z  cloaked    сост.  pid    exe                rect                     класс                      заголовок
    57  —          normal 22164  Code.exe           1058,44 2565x1372        Chrome_WidgetWin_1         Открыть PLAN.md - IAR (рабочая область) - Visual Studio Code
    95  —          normal 12368  explorer.exe       206,1819 572x334         CabinetWClass              T:\
          папка  T:\
   118  —          normal 12368  explorer.exe       2099,1818 584x340        CabinetWClass              E:\PCAD\ScreenMemory\bin
          папка  E:\PCAD\ScreenMemory\bin

  [3] «ESP32» — окон 20
     z  cloaked    сост.  pid    exe                rect                     класс                      заголовок
    76  shell      normal 17084  chrome.exe         1149,225 1288x1363       Chrome_WidgetWin_1         DeepSeek - В неизвестность - Google Chrome
    85  shell      normal 12368  explorer.exe       860,1642 563x333         CabinetWClass              C:\temp
          папка  C:\temp
```

* `z` — позиция в z-order всего экрана (0 — самое верхнее окно); по этому же порядку
  считается поле `zg` в файле раскладки;
* `cloaked` — `—` обычное окно, `shell` — окно на другом виртуальном столе (то, ради чего
  всё и сохраняется), `app` — окно спрятало само приложение (UWP в suspended),
  `inh` — унаследованно накрытое (такие отбрасываются);
* `сост.` — `normal` / `max` / `min` из `GetWindowPlacement` — это и есть показ окна,
  который восстанавливается;
* `rect` — видимые границы окна (`DWMWA_EXTENDED_FRAME_BOUNDS`), координаты общие для всех
  мониторов, т.е. абсолютные;
* `pid` — процесс-владелец окна; в `--verbose` печатается ещё и `hwnd`;
* `exe` — имя файла процесса окна (`Code.exe`); если оно длиннее колонки, хвост
  заменяется на `…`, полный путь есть только в `--verbose`;
* `папка` — отдельной строкой под окном Проводника: именно папка, а не заголовок —
  главный ключ восстановления, потому что заголовки у окон Проводника повторяются;
* `place` — отдельной строкой под окном, которое свёрнуто или развёрнуто: «нормальная»
  позиция окна (`rcNormalPosition` из `WINDOWPLACEMENT`). Для таких окон колонка `rect`
  ничего не говорит о том, куда окно вернётся: у свёрнутого это служебные `-32000`,
  у развёрнутого — весь монитор. В файл раскладки пойдёт именно `place`.

В `--verbose` под каждым окном дополнительно печатаются `exe` (полный путь),
`cmd` (командная строка) и `aumid` — по ним `restore` будет запускать недостающие окна.
В конце сводки есть строка `exe прочитан у 60, AUMID — у 16, папка Проводника — у 34`:
`exe` читается у всех окон, AUMID есть только у приложений из Microsoft Store
и у некоторых Chromium-сборок, папка — только у окон Проводника.

Окна удалённого доступа и виртуальных машин — обычные окна: `mstsc.exe`
(класс `TscShellContainerClass`) сохраняется вместе с командной строкой
(`mstsc.exe "…\Подключение.rdp"`), `VirtualBox.exe` (менеджер) и `VirtualBoxVM.exe`
(запущенная ВМ, Qt-класс `Qt653QWindowIcon`) — с exe и геометрией. У `VirtualBoxVM`
командная строка — внутренняя (`…-suplib-3rdchild --startvm <GUID>`), повторно она
не запускается: для запуска нужен `VirtualBoxVM.exe --startvm <GUID>`, и этот GUID
в сохранённой строке есть. Служебные окна этих программ (общий буфер обмена, сторож
смены экранов, IME) отсеиваются как невидимые или `WS_EX_TOOLWINDOW`.

Папку окна Проводника программа узнаёт двумя способами: через COM-коллекцию
`IShellWindows` и — для окон на **неактивных** виртуальных столах — по заголовку окна.
Причина: `IShellWindows` перечисляет только окна текущего стола (на проверочной машине
15 элементов при 34 открытых окнах Проводника). Заголовок принимается, только если
по нему действительно есть существующий каталог, поэтому для виртуальных папок
(«Быстрый доступ», библиотеки) папка остаётся неопределённой — это ожидаемо.

Группа «маркер pinned-окон» — это как раз pinned-приложения: они не принадлежат ни одному
десктопу и отдают GUID, которого нет в списке `VirtualDesktopIDs`. Поэтому такие окна
не переносятся между десктопами (они и так видны везде), а при определении текущего
десктопа их голос не учитывается.

Окнами не считаются: невидимые окна, `WS_EX_TOOLWINDOW`, owned-окна (кроме диалогов
с заголовком), служебные классы оболочки (`Progman`, `WorkerW`, панели задач,
`Windows.UI.Core.CoreWindow` и т.п.), окна без заголовка (кроме Проводника, UWP-рамки
и диалогов) и пустые UWP-рамки `ApplicationFrameWindow` без содержимого — Explorer держит
по одной такой на каждый монитор.

### Особенности определения текущего десктопа

Способы перебираются по порядку, в строке «текущий десктоп:» видно, какой сработал —
`(по: окно в фокусе)`, `(по: консольное окно)`, `(по: голосование по окнам (12 из 14))`:

1. окно в фокусе (`GetForegroundWindow` и его корневой владелец);
2. консольное окно (`GetConsoleWindow`);
3. голосование по окнам — учитываются только видимые и не «затемнённые» DWM окна,
   для каждого проверяется `IsWindowOnCurrentVirtualDesktop`, побеждает десктоп
   с большинством окон;
4. окна оболочки: рабочий стол (Progman) и панели задач (`Shell_TrayWnd`,
   `Shell_SecondaryTrayWnd`);
5. значение `CurrentVirtualDesktop` в реестре (на Windows 10 22H2 его нет).

Терминалы вроде ConEmu заводят собственное окно класса `VirtualConsoleClass`, у которого
может не быть записи в диспетчере виртуальных десктопов: обращение к нему возвращает
`0x8002802B (TYPE_E_ELEMENTNOTFOUND)`. Именно из-за этого программа раньше «не видела»
текущий десктоп при запуске из ConEmu; теперь такой отказ просто передаёт управление
следующему способу, и десктоп всё равно определяется.

Если строка всё-таки говорит «не определён»:

* запустите `ScreenMemory.exe --list --verbose` — в лог `T:\ScreenMemory\screenmemory.log`
  пишется диагностика `диагностика десктопа: фокус=…, консоль=…, голосование=…,
  оболочка=…, реестр=…`, то есть результат каждого способа и точные HRESULT отказов;
* «не определён» штатно бывает на пустом рабочем столе — там нет ни одного окна,
  кроме собственного окна терминала;
* если окна есть, а десктоп не найден, пришлите этот лог.

## Сохранение раскладки: `ScreenMemory.exe save`

`save` снимает слепок всех нормальных верхнеуровневых окон и пишет его в
`bin\layout.txt` рядом с exe (а не в текущий каталог — иначе запуск из Планировщика
задач ломал бы пути). Окна берутся со **всех** виртуальных десктопов, включая те,
что прямо сейчас не показаны.

```
> bin\ScreenMemory.exe save
Слепок сохранён: E:\PCAD\ScreenMemory\bin\layout.txt
  десктопов 5, мониторов 2, окон 57 (pinned 5)
  кандидатов 60 из 832 верхнеуровневых окон, дублей пропущено 3 (копии уже записанных окон)
  браузеров 15, адрес страницы прочитан у 15
```

Строки про предыдущую версию и удалённые старые версии печатаются только с `--verbose`:
они появляются при каждом `save` и ничего не сообщают.

Каждый `save` сдвигает предыдущий слепок в `layout-YYYY-MM-DD_HH-MM-SS.txt`
(время берётся из заголовка `# saved=` самого слепка) и оставляет **5** самых новых
версий, остальные удаляются. Откат — вручную: переименуйте нужный `layout-*.txt`
в `layout.txt` (или отредактируйте `layout.txt` руками: формат читаемый, см.
`PLAN.md` §6) и запустите `restore`.

**Если раскладка не изменилась, файл не перезаписывается.** Перед записью `save` читает
текущий `layout.txt` и сравнивает его с тем, что видит сейчас: совпало — печатается
`Слепок не изменился с 2026-11-15T18:04:12 — файл не переписан`, и ни `layout.txt`, ни
ротация не трогаются (важно для задачи `AutoSave`, которая срабатывает каждые 10 минут:
без этого диск писался бы впустую). Сравниваются десктопы, мониторы, разрешение экрана и
все поля окон как множество — порядок записей не важен; не сравниваются `zg` (z-order
меняется от каждого клика по окну, и переписывать из-за него файл бессмысленно) и строка
`# saved=`. С причиной отличия можно разобраться по `--verbose`: там печатается, что именно
изменилось (`LayoutDiffReason`) — «окно «…»: новое», «монитор …: другие границы».

Что попадает в файл:

* `[desktop.N]` — все десктопы на момент сохранения (имя — главный ключ, номер и GUID — запасные);
* `[monitor.N]` — мониторы: device-имя, положение, рабочая область, DPI;
* `[window.N]` — по записи на окно: десктоп, `pinned`, z-order, exe, cmdline, класс,
  папка Проводника, заголовок, AUMID, монитор-якорь, координаты `mrel`/`rect`, состояние,
  `url` — адрес вкладки браузера (только у браузеров и только если его удалось прочитать).

Адрес страницы (`url=`) — единственный способ восстановить окно браузера: в командной
строке процесса его нет, Chrome хранит адрес в профиле. Читается через UI Automation:
у Chrome/Edge адресная строка — `Edit` с `ValuePattern`, у Firefox — `ComboBox`, у которого
значение лежит на самом ComboBox (`AutomationId` = `urlbar-input`). Признак адресной
строки — имя контрола («Адресная строка и строка поиска», «Найдите в Google или введите
адрес») или `AutomationId` (`urlbar`, `omnibox`, `address`); значение берётся через
`ValuePattern`, а если его нет — через `LegacyIAccessiblePattern`. Если прочитать не
удалось, запись остаётся без `url=` и при `restore` не запускается (подробности —
`bin\admin.log`, `browser-no-url`).
Адрес используется дважды: при запуске закрытого окна (`--new-window "<url>"`) и при
сопоставлении живых окон — `restore` читает адрес открытой страницы у окон браузеров и
сверяет с файлом (совпал — сильный признак, разный — окно считается чужим и не
перетаскивается; в `--verbose` такой признак виден как `url` в списке совпадений).

Браузер, который восстанавливает сессию профиля (Firefox), при холодном старте ведёт себя
иначе, чем остальные: `-new-window "<url>"` у него оказывался лишней вкладкой в восстановленном
окне, а на текущем столе оставалось пустое окно «Новая вкладка». С 0.8.4 `restore` сначала
поднимает браузер **без адреса**, даёт ему 2.5 с на восстановление сессии и только потом
открывает новое окно с сохранённым адресом; окно ищется по адресу страницы (у Firefox окно
создаёт уже работающий процесс, поэтому «первое новое окно класса» могло оказаться окном
сессии), а пустые окна, которые браузер открыл сам, закрываются. Само окно восстановленной
сессии `restore` не трогает — в нём могут быть ваши вкладки.

Координаты хранятся дважды: `mrel` — относительно угла своего монитора (по нему идёт
восстановление, поэтому смена раскладки мониторов не сдвинет окна) и `rect` —
абсолютные, для сверки и диагностики. Для развёрнутых и свёрнутых окон в файл пишется
**нормальная** позиция окна (`rcNormalPosition`), а не текущая: у развёрнутого окна
текущие границы — это весь монитор, у свёрнутого — служебные `-32000`.

Pinned-приложения («показывать на всех рабочих столах») пишутся один раз, с `pinned=1`;
их `desktop` — тот стол, на котором окно было видно. Дубли (одинаковые exe/класс/
заголовок на одном столе и почти те же координаты) отбрасываются — это и есть число в
строке `дублей пропущено N (копии уже записанных окон)`: пропускаются служебные копии окна
(панель предпросмотра, скрытый клон), а не теряется запись. Если пропускать нечего, число
и пояснение не печатаются вовсе.

Ключ `--verbose` печатает подробный лог сбора, а после записи читает файл обратно и
сообщает о расхождениях (`самопроверка: файл прочитан обратно без расхождений`) —
это защита от ошибок экранирования заголовков и путей.

## Восстановление раскладки: `ScreenMemory.exe restore`

`restore` читает `bin\layout.txt` и приводит рабочий стол к сохранённому виду: возвращает
каждое найденное окно на свой виртуальный десктоп, ставит сохранённые координаты, размер,
состояние (обычное / развёрнутое / свёрнутое) и порядок наложения окон, а приложения,
окон которых нет, запускает (кроме консолей — см. `bin\admin.log`).

```
> bin\ScreenMemory.exe restore
ScreenMemory 0.8.4
каталог: E:\PCAD\ScreenMemory\bin

Раскладка: E:\PCAD\ScreenMemory\bin\layout.txt
  сохранена 2026-11-13T18:27:42; десктопов 5, мониторов 2, окон 63

Десктопы: в файле 5; по GUID 0, по имени 4, по индексу 1, fallback 0
  [0] «Работа» → [0] «Работа»   по: имя
  [1] «AliExpress» → [1] «AliExpress»   по: имя
  [2] «Game» → [2] «Game»   по: имя
  [3] «ESP32» → [3] «ESP32»   по: имя
  [4] (без имени) → [4] (без имени)   по: индекс

  применено: 0000000001271DA2 «Alcohol-LCD.md - MarkDown (рабочая область) - Visual Studio Code» → 4424,536,6629,1784, стол [0]
  ...
  запущено: phaseb_probe.txt – Блокнот               → 607,703,1537,1751  стол [0] «Работа»
  запущено: E:\PCAD\Robe\Web\public\Для_Своих\img    → 3262,1806,3846,2168  стол [0] «Работа»

Применено: 62, перенесено на другой десктоп: 0, z-order выставлен: 64
Запущено: 2, не удалось поднять: 0, не запускается: 0
ВНИМАНИЕ:   не удалось восстановить: 2 (подробности выше)
  требуют вмешательства человека: 2 — открываю E:\PCAD\ScreenMemory\bin\admin.log
```

Что и в каком порядке делается:

1. **Десктопы сопоставляются по имени** — человек, давая десктопу имя, связывает его с тем, что
   на нём открыто, поэтому имя главнее GUID. Если десктопа с таким именем нет, ищется десктоп
   по **номеру** (индекс в Task View: «третий слева»), и только потом — по **GUID**. GUID
   переживает переименование и перестановку десктопов, но ничего не говорит о содержимом,
   поэтому он замыкает цепочку: в отчёте такая пара помечается `переименован`. Если не
   нашлось ничего, окна идут на **первый** десктоп — в отчёте `fallback`. Имена в программе
   не зашиты, имя, которого нет в системе, печатается как `имени нет в системе`.
2. **Окна сопоставляются с записями** по сумме признаков: путь `exe` (100 баллов), класс
   окна (50), AUMID (60), адрес вкладки браузера (60), папка Проводника (40), точный
   заголовок (40), десктоп (25/10), близкие координаты (20). Пара принимается с 100 баллами
   (совпал exe) либо с 90 для Проводника (класс + папка). Окна одного приложения различаются
   по заголовку, папке и координатам; если папка Проводника у записи и у окна известна и
   разная, пара не рассматривается вовсе — чужое окно не «уедет» на место потерянного.
   То же для адреса вкладки: у браузеров `restore` читает адрес открытой страницы, и если он
   отличается от сохранённого, пара отклоняется — нужная страница откроется отдельным окном,
   а чужое окно останется на месте. И ещё одно правило на тот случай, когда данные окна не
   различают: если несколько окон одного приложения дали одинаковый максимальный балл, сидят
   на **разных** десктопах и ни заголовок, ни папка, ни адрес их не разделяют, пара не
   создаётся вовсе (в отчёте `неоднозначно: N записей — одинаковые окна на разных десктопах
   не сопоставлены`). Окна остаются на своих столах, а записи уходят в фазу B: лишнее окно
   лучше, чем окно с чужим содержимым на неверном столе. Время здесь не экономится — окна
   одного приложения с разных столов не должны меняться местами.
3. **Геометрия** восстанавливается через `SetWindowPlacement` — это единственный корректный
   способ вернуть и «нормальную» позицию, и состояние. Координаты берутся из `mrel`
   (смещение от угла своего монитора), поэтому смена места мониторов, primary-монитора
   или разрешения не сдвигает окна; при смене DPI монитора координаты пересчитываются.
   Если монитор-якорь отключён, программа использует абсолютные координаты, а если и они
   не попадают ни на один монитор — ставит окно на primary, сохраняя относительную позицию.
4. **Перенос на десктоп** — окно возвращается на свой рабочий стол через внутренний интерфейс
   оболочки (`CLSID_ImmersiveShell` запрашивается как `IServiceProvider`, затем
   `IVirtualDesktopManagerInternal::MoveViewToDesktop` по `IApplicationView` окна), потому что
   документированный `MoveWindowToDesktop` переносит только окна собственного процесса и для
   всех остальных отвечает «отказано в доступе». `QueryService` обязан запрашивать именно
   `IID_IServiceProvider`: если попросить `IID_IUnknown`, слот `QueryService` в полученной
   vtable окажется другим, и процесс упадёт с переполнением стека. Индексы слотов считаются
   по фактической таблице (`0…2` — методы `IUnknown`), поэтому `GetViewForHwnd` — слот 6,
   `MoveViewToDesktop` — 4, `FindDesktop` — 12. Результат проверяется: если
   окно не оказалось на нужном столе, делается до трёх попыток, и только потом в `admin.log`
   появляется `move-desktop-failed`. Окна, помеченные «показывать на всех рабочих столах»,
   не переносятся (они и так видны везде). Окно, которое уже на месте, лишний раз не трогается.
5. **Порядок наложения** восстанавливается поднятием окон (`SetWindowPos HWND_TOP` без
   активации), поэтому фокус не отбирается.
6. **Запуск отсутствующих окон** — приложения, окон которых нет, запускаются и сразу
   расставляются: Проводник открывается по сохранённой папке, UWP активируется по AUMID,
   VirtualBox — по `--startvm <GUID>`, браузер — по адресу страницы (`"<exe>" --new-window
   "<url>"`, у Firefox `-new-window`, у IE без ключа), остальные — по сохранённой командной
   строке или по пути к exe. Адрес активной вкладки читается при `save` через UI Automation
   и хранится в `layout.txt` полем `url=`; браузерная запись без адреса не запускается вовсе
   (`browser-no-url`), потому что пустое окно или чужая вкладка хуже ручной работы. Окно
   ищется по PID, точному заголовку или по «новому окну нужного класса»
   (Проводник и UWP создают окно в уже работающем процессе и сами выбирают заголовок —
   например, у папки `…\img` заголовок `img`). Приложение, помеченное «показывать на всех
   рабочих столах», второй раз не запускается, если уже работает. Окна ждём до 60 секунд и
   прекращаем ждать досрочно только если процесс завершился: приложения открывают окно
   заметно позже старта, а спешить нам некуда. Если окно всё-таки не появилось — строка
   `launch-timeout` в `bin\admin.log`. Браузер к тому же показывает окно раньше, чем
   открывает страницу, поэтому перед переносом его окна программа ждёт, пока адрес станет
   непустым и перестанет меняться (до 30 секунд): тащить окно в момент навигации — это
   спешка, которой у нас нет причин.

### Что не перезапускается: `bin\admin.log`

Часть окон восстановить программно нельзя, и они попадают в журнал `bin\admin.log` рядом
с exe. С 0.8.3 строка журнала — это **готовая команда для `cmd.exe`**: её достаточно
скопировать из блокнота в консоль, чтобы получить окно на своём рабочем столе. Заголовок,
причина и имя десктопа в файл не пишутся — их показывает отчёт `restore` в консоли:

```
"C:\Program Files\OpenConnect-GUI\openconnect-gui.exe"
"C:\Windows\SYSWOW64\Taskmgr.exe"
"C:\Program Files (x86)\Google\Chrome\Application\chrome.exe" "https://ikrut.pro/Water2/"
```

Почему окно в журнале:

* `move-blocked` — окно приложения, запущенного от администратора: Windows тихо игнорирует
  перемещение такого окна из обычного процесса (UIPI), либо `SetWindowPlacement` отвечает
  «Отказано в доступе». Такое окно нужно поставить руками или запустить программу от админа;
* `move-desktop-failed` — окно не удалось перенести на нужный рабочий стол ни внутренним
  интерфейсом оболочки, ни документированным API (после трёх попыток оно осталось на прежнем
  столе);
* `launch-elevation-required` — приложение требует повышения прав, `CreateProcessW` вернул
  `ERROR_ELEVATION_REQUIRED`;
* `launch-failed` — процесс не запустился или окно не удалось расставить;
* `launch-timeout` — процесс запущен, но окно не появилось;
* `browser-no-url` — браузер, у которого при `save` не удалось прочитать адрес активной
  вкладки (закрыт доступ к UI Automation, окно ещё не отрисовано): запуск без адреса открыл
  бы пустое окно, поэтому запись не перезапускается;
* `console` — консольные окна (`cmd`, ConEmu, Windows Terminal) намеренно не перезапускаются:
  в слепке известна только командная строка хоста, а что было запущено внутри — нет;
* `no-command` — по записи не из чего собрать команду запуска.

Строки с этой машины (прогон 0.8.3, окна админ-приложений):

```
"C:\Program Files\OpenConnect-GUI\openconnect-gui.exe"
"C:\Windows\SYSWOW64\Taskmgr.exe"
```

У браузера в журнале к пути добавлен адрес страницы — команда открывает её в текущем окне
(отдельное окно с `--new-window` создаёт только автоматический запуск фазы B):

```
"C:\Program Files\Google\Chrome\Application\chrome.exe" "https://ikrut.pro/Water2/"
```

До 0.8.3 строки выглядели как `<exe> | <заголовок> | <причина> | desktop=<имя>`; причины и
заголовки никуда не делись — они печатаются в отчёте `restore` перед открытием журнала.

Журнал описывает **только последний запуск** `restore`: файл перезаписывается целиком при
каждом прогоне (поэтому метки времени в строках нет — различать нечего), а если записей за
запуск не появилось, старый файл удаляется. Файл пишется в UTF-8 с BOM, так что кириллица в
блокноте читается (без BOM блокнот принимает UTF-8 за ANSI и показывает мусор).

Если записи есть, `restore` в конце открывает журнал в блокноте. Открытое окно блокнота с
`admin.log` от прошлого прогона перед этим закрывается (`WM_CLOSE`), поэтому на экране всегда
одно окно — и в нём свежая сессия, а не прошлая (блокнот сам файл не перечитывает).

Код возврата в таком случае будет `1`: работа сделана, но часть окон осталась за человеком.

### Безопасная проверка: `restore --dry-run`

```
> bin\ScreenMemory.exe restore --dry-run
```

Печатает ту же карту десктопов и полный план по каждому окну — «текущая позиция → целевая,
стол, состояние, перенос, поправки» — но **ничего не меняет**: план строится теми же
функциями, что применяют изменения, поэтому увиденное совпадает с тем, что сделает
настоящий `restore`. Удобно, когда не хочется, чтобы окна «прыгали», пока идёт работа.

Пример строки плана: `UPDK - Google Chrome  664,1 847x1082 → 664,1,1511,1083  стол [0] «Работа»  normal`.
Слева — нормальная позиция окна сейчас (`rcNormalPosition`), справа — целевая из слепка.
Для отсутствующих приложений печатается `запустил бы: <чем> <команда> → стол [N] …` —
ровно то, что сделает настоящий `restore`, но без запуска процессов и перемещения окон.

Коды возврата `restore`: `0` — всё применилось, `1` — часть окон применить не удалось или
часть окон уехала на десктоп 0 (их сохранённых десктопов нет в системе), `2` — нет
`layout.txt` или файл битый, `3` — не удалось получить список десктопов.

У `AutoSave`/`AutoRestore`/`Uninstall`: `0` — задача поставлена (или снята) и в `--dry-run`
проверка прошла, `1` — планировщик отказал (текст ошибки печатается), `5` — не хватило прав
администратора, `64` — неверная командная строка.

### Окна, которым не нашлось места: `fallback-desktop`

Если сохранённый десктоп удалён (или переименован и пересоздан с другим GUID, а по имени
не нашёлся), его окна ставятся на **первый** десктоп — в тех же координатах. Это видно
двумя строками отчёта:

```
Оказалось на десктопе 0 (целевой десктоп не найден): 27
ВНИМАНИЕ:   окон на десктопе 0: 27 — сохранённых десктопов нет в системе; пересохраните раскладку после возврата десктопов
```

В `--dry-run` та же величина печатается как «уехало бы на десктоп 0 …: N» — можно
посмотреть заранее, сколько окон пострадает. Pinned-окна в счётчик не попадают (они видны
на всех столах и никуда не уезжают), а окна, которые применить не удалось, считаются
ошибками (`не удалось восстановить: N`). Наличие таких окон даёт код возврата `1`:
раскладка восстановлена, но часть её потеряла свой стол.

## Если exe перестал запускаться

Сообщения «Не удалось запустить это приложение на вашем ПК» или «Отказано в доступе»
при запуске `ScreenMemory.exe` обычно означают, что файл повреждён. Проверьте размер:
`dir bin\ScreenMemory.exe` — должно быть около 400 КБ. Если там 0 байт, достаточно
пересобрать: `build.bat`. Так бывает после случайной вставки в консоль строки
с перенаправлением вывода (`> bin\ScreenMemory.exe`).

## Ярлыки на рабочем столе

`ScreenMemory.exe` содержит две иконки: первая (дискета) — «сохранить», вторая
(окно со стрелкой) — «восстановить». При создании ярлыка: правый клик → Свойства →
Ярлык → `save` или `restore` в поле «Объект» → «Сменить значок» → выбрать
`ScreenMemory.exe` → в списке будут обе иконки.

## Автозапуск: `AutoSave`, `AutoRestore`, `Uninstall`

Автозапуск ставится не сам, а тремя командами — когда вы этого захотите. Всё — через
Планировщик заданий, от имени текущего пользователя (задача создаётся без пароля, поэтому
Windows не спрашивает его каждые 10 минут). **Эти три команды нужно запускать от имени
администратора**: без прав задача печатает «нужны права администратора» и возвращает код 5 —
Планировщик не даёт менять свои задания обычному пользователю.

```
bin\ScreenMemory.exe AutoSave       задача «ScreenMemory AutoSave»: «<exe> save --hidden»
                                    каждый день, повторять каждые N минут (по умолчанию 10)
bin\ScreenMemory.exe AutoRestore    задача «ScreenMemory AutoRestore»: «<exe> restore --hidden»
                                    триггер «При входе в систему» + задержка (по умолчанию 30 с)
bin\ScreenMemory.exe Uninstall      снять обе задачи и значение ScreenMemory из
                                    HKCU\...\CurrentVersion\Run (если ставили вручную)
```

Сначала полезно посмотреть, что будет сделано, — `--dry-run` ничего не меняет:

```
> bin\ScreenMemory.exe AutoSave --dry-run
ScreenMemory 0.9.0
каталог: E:\PCAD\ScreenMemory\bin

Проверка (ScreenMemory AutoSave): ничего не регистрирую
  задача: «ScreenMemory AutoSave» — каждые 10 мин
  XML задачи: C:\temp\ScreenMemory-AutoSave.xml
  зарегистрировать вручную: schtasks /Create /TN "ScreenMemory AutoSave" /XML "C:\temp\ScreenMemory-AutoSave.xml" /F
```

Для `AutoRestore` в тех же строках печатается «при входе в систему, задержка 30 с», для
`Uninstall` — что именно найдено (или «автозапуск не установлен — снимать нечего»). XML
задачи можно зарегистрировать и руками приведённой командой `schtasks`.

Что внутри XML и правильно ли он собран, видно и без прав администратора:
`powershell -File tools\check_task_xml.ps1` проверяет оба файла (BOM, схема, пользователь,
`InteractiveToken`, `IgnoreNew`, лимит времени, триггер и команду — значения интервала и
задержки берутся из `Config.ini`), а `-Register` дополнительно убеждается, что Планировщик
этот XML принимает: регистрирует копию под временным именем и сразу снимает её.

Про права чуть точнее: задача с триггером «при входе в систему» требует администратора —
так устроена Windows (проверено и `schtasks /SC ONLOGON`, и тем же XML с заменой триггера на
обычное расписание: без прав «Отказано в доступе» даёт только триггер входа). Задачу
`AutoSave` Планировщик принимает и без повышения, но все три команды требуют администратора
сознательно: `Uninstall` снимает в том числе задачу входа, а «одна команда — одни права»
понятнее, чем «эта работает, эта нет».

Интервал и задержка берутся из `Config.ini` (`AutoSave`, `AutoRestoreDelay`) в момент
создания задачи: поправили файл — выполните команду ещё раз, задача перезапишется.

Зачем задержка у `AutoRestore`: приложения из автозагрузки должны успеть открыть свои окна
сами, иначе `restore` поднимет их сам, а потом приложение откроет второе окно. Меньше
20 секунд ставить смысла нет.

`--hidden` прячет окно консоли и не ждёт клавишу — так программу и запускают задачи; при
`--hidden` лог ведётся всегда (`T:\ScreenMemory\screenmemory.log`), иначе ошибка фонового
запуска пропала бы молча.

Если задан `prelaunch` (см. «Настройки: `Config.ini`»), задача «При входе в систему» будет
ждать, пока вы не закроете окно программы мониторов: либо закрывайте его сами, либо задайте
`prelaunch-timeout` (например, `120`) — по истечении этого времени `restore` продолжит работу.

Почему `AutoSave` не изнашивает диск: `save` не переписывает файл, если раскладка не
изменилась (см. «Сохранение раскладки»). Плюс ручной `save` перед перезагрузкой всё равно
полезен: задача раз в 10 минут может не успеть записать последние изменения.

Отдельно про права: команды `save` и `restore` **никогда** не запрашивают администратора —
окна приложений, запущенных от админа, они не смогут переместить. Такое окно попадает в
отчёт строкой «позиция не применилась» или «Отказано в доступе», пишется в `bin\admin.log`
(причина `move-blocked`), и в конце `restore` этот журнал открывается в блокноте. Это же
касается консолей: что было запущено внутри, из слепка неизвестно, поэтому такие окна не
перезапускаются, а попадают в журнал с причиной `console`.

Программу придумал **iKRUT** — [ikrut.pro](https://ikrut.pro). Что она должна делать (слепок
нескольких рабочих столов, возврат окон на места, перезапуск приложений, автозапуск через
Планировщик) и как вести себя в спорных случаях — его постановка. Проверки на живой машине,
решения «так удобнее» и «так не надо» — тоже его.

Исполнил всё это **Cline**, AI-ассистент для программирования: он работает внутри редактора и
сам читает и правит файлы проекта, запускает сборку и проверки, ведёт `PLAN.md` и `CONTEXT.md`.
Если коротко — это исполнитель, который смотрит в код, а не догадывается о нём. В этом проекте
на нём архитектура (Win32 API, без сторонних библиотек), весь код в `src\*.cpp`, `build.bat`,
`tests\smoke.bat`, `tools\check_exe.ps1`, `tools\check_task_xml.ps1` и вся документация.
Каждый шаг заканчивался сборкой и прогоном проверок, а не обещанием, что «должно работать»:
так нашлись и лишняя запись `layout.txt` при неизменившейся раскладке, и отказы Планировщика
без прав администратора.
