# PLAN — ScreenMemory (сохранение/восстановление раскладки окон по виртуальным рабочим столам)

Статус: план утверждён. **Этапы 1–11 готовы (версия 0.9.2), кроме проверки на реальной перезагрузке**: собирается `bin\ScreenMemory.exe` с двумя иконками,
работают справка, коды возврата, `--list` (десктопы из реестра + pinned-приложения + надёжное
определение текущего десктопа, в том числе под ConEmu + окна всех десктопов с cloaked-флагом,
состоянием, координатами, `exe`/`cmdline`/AUMID и папкой окон Проводника + карта десктопов из
`layout.txt`), `save` (слепок в `bin\layout.txt`: десктопы, мониторы, окна; атомарная запись +
ротация рабочих версий и защищённые копии «вчерашний день» / «прежняя конфигурация») и `restore` всех трёх фаз: чтение слепка, карта десктопов GUID → имя → индекс →
fallback, жадный матчинг окон, геометрия через `SetWindowPlacement` с пересчётом `mrel`/DPI и
прижиманием в монитор, перенос на нужный стол (`MoveWindowToDesktop`; pinned не переносим),
запуск отсутствующих приложений и окон Проводника (фаза B), z-order и `--dry-run`, печатающий
план без единого изменения. Всё, что требует ручной работы (окна админ-приложений, консоли),
пишется в `bin\admin.log` (файл описывает только последний запуск и перезаписывается), и файл
открывается в блокноте. Окна без своего десктопа учитываются отдельным счётчиком `fallback-desktop`
и дают код возврата 1.
Этап 9 тоже готов: `README.md` описывает все команды, автозапуск ставится по желанию —
`AutoSave`, `AutoRestore`, `Uninstall` (Планировщик заданий, нужны права администратора), а от
частых срабатываний `AutoSave` файл слепка защищён сравнением с уже записанным
(`SameLayoutContent`: не изменилось — файл не переписывается). Этап 10 (0.9.1) добавил
защищённые копии слепка: «цепочку дней», которую двигает `restore` при старте новой сессии,
«прежнюю конфигурацию», которую двигает `save` при смене мониторов или десктопов, ключ
`Layouts` и `restore --from <файл>`. Этап 11 (0.9.2) убрал дубли окон после перезагрузки:
фаза B ждёт «успокоения» окон (`settle-wait`) и перед каждым запуском перепроверяет запись
через `MatchRecord` — если нужное окно открылось само, оно ставится на место, а второй
экземпляр приложения не запускается (§8.3 п.0, CONTEXT п. 69). Осталась финальная проверка
глазами пользователя: «save → перезагрузка → restore».

Среда: Windows 10 Pro 22H2 (build 19045.6456), x64, MSVC 14.24 (VS2019 Community), Windows SDK 10.0.18362.

## 1. Цель

Утилита на C++ / WinAPI (MSVC x64), которая:

* `save` — снимает «слепок» всех нормальных верхнеуровневых окон: приложение, заголовок, класс, координаты/размер, состояние (normal/maximized/minimized), z-order, **на каком виртуальном десктопе** окно находится (по имени и по индексу), признак «показывать на всех десктопах» (pinned), а для окон Проводника — путь папки. Пишет это в обычный текстовый файл рядом с `.exe`, ротирует до 3 предыдущих версий (ключ `Layouts`) и отдельно хранит защищённые копии: «прежнюю конфигурацию» при смене мониторов/десктопов (§6.1).
* `restore` — читает файл и восстанавливает: запускает отсутствующие приложения, ставит окна в сохранённые координаты, возвращает каждое окно на его виртуальный десктоп (матчинг по GUID → имени → индексу, при отсутствии десктопа — на первый/нулевой, координаты те же), pinned-приложения восстанавливает в единственном экземпляре.

Десктопы на текущей машине подписаны `Работа`, `AliExpress`, `Game`, `ESP32` — это пример, а не константы: количество и имена любые, главный ключ восстановления — GUID десктопа, имя вспомогательное, индекс резервный.

### 2.1 Реестр — источники данных (документированные ключи, без хакерства)

* `...\Explorer\VirtualDesktops\VirtualDesktopIDs` — `REG_BINARY`, 16 байт на десктоп, **в порядке отображения**. В нашем случае:
  * индекс 0 — `{3BBD80D8-D12B-4B44-AC94-2579E6984975}` → имя `Работа`
  * индекс 1 — `{09D112DA-0BB6-4073-8A33-63EFF448696E}` → имя `AliExpress`
  * индекс 2 — `{D7B24E7A-F0FF-435E-BA53-55D2EFDC7A32}` → имя `Game`
  * индекс 3 — `{4AD61A74-9B8C-4F97-AFC3-C09DDC97FF33}` → имя `ESP32`
  (GUID читаются как GUID: первые 3 поля little-endian; проверим `list`-командой на этапе 2.)
* `...\VirtualDesktops\Desktops\{GUID}\Name` — `REG_SZ`, имя десктопа (пусто/нет значения = десктоп без имени).
* `...\VirtualDesktops\PinnedApps` — значения `REG_DWORD` (=0), **имена значений** — путь exe или AppUserModelID приложений «показывать на всех рабочих столах». Вывод: **pinned-статус и имена десктопов можно получать из реестра** — недокументированные COM-интерфейсы `twinui.dll`/`ImmersiveShell` для MVP не нужны. Документированный `IVirtualDesktopManager` нужен только для: (а) GUID десктопа конкретного окна (`GetWindowDesktopId`), (б) переноса окна на другой десктоп (`MoveWindowToDesktop`).

## 3. Требования (сводка из CONTEXT.md, включая уточнения 14–18)

1. Запоминать/восстанавливать позицию, размер и состояние окон, включая открытые на **других** виртуальных десктопах.
2. Запоминать, какое окно на каком десктопе было.
3. Восстанавливать окна Проводника **на каждом** десктопе (одна и та же папка может быть открыта на нескольких).
4. Pinned-приложения не размножать: один экземпляр, «на всех десктопах».
5. Один `.exe` с параметром `save` / `restore`.
6. Данные — в обычном текстовом файле в папке с `.exe`.
7. **Десктопы идентифицируются по имени**, при отсутствии имени — по индексу (первый = 0).
8. **Нет нужного десктопа → окно открывается на нулевом (первом) десктопе в тех же координатах.**
9. **Хранить 5 версий файла координат** (с ротацией) для ручного отката.
10. Максимально опираться на реестр вместо недокументированных API.
11. C++ + Microsoft WinAPI, сборка MSVC.
12. Временные файлы — на `T:` (RAM-диск), не мусорить на SSD.

## 4. Сборка (реализовано в `build.bat`)

`build.bat` (запускать из корня проекта; `cl.exe` в PATH нет):

1. Находит `vcvars64.bat` через `vswhere.exe` (фолбэк — путь VS2019 Community) и вызывает его.
2. Создаёт `T:\ScreenMemory\obj` (объектники и PDB на RAM-диске) и `bin`.
3. Если нет `bin\save.ico`/`bin\restore.ico` — запускает `tools\make_icons.ps1`.
4. `rc.exe` → `T:\ScreenMemory\obj\app.res`.
5. `cl.exe` с флагами:

   ```
   /W4 /std:c++17 /EHsc /O2 /MT /permissive- /utf-8
   /DUNICODE /D_UNICODE /D_WIN32_WINNT=0x0A00 /DWINVER=0x0A00
   src\*.cpp T:\ScreenMemory\obj\app.res
   /link /SUBSYSTEM:CONSOLE /MANIFEST:EMBED /MANIFESTINPUT:ScreenMemory.manifest
   user32 dwmapi ole32 oleaut32 shell32 shlwapi psapi propsys advapi32
   ```

* x64, `/MT` — статический CRT, exe не требует распространяемый пакет VC++.
* `/utf-8` обязателен: исходники в UTF-8, иначе русский текст в консоли станет мусором.
* `ScreenMemory.manifest`: `dpiAwareness = PerMonitorV2` (+ `dpiAware=true/PM`), common-controls v6, права `asInvoker` (см. п. 9.3 про elevated-окна).
* Объектники и PDB — в `T:\ScreenMemory\obj`, чтобы не изнашивать SSD.
* `clean.bat`: удаляет `bin\ScreenMemory.exe` и `T:\ScreenMemory\obj\*`; иконки остаются.
* Кодировки: исходники — UTF-8 (собираются с `/utf-8`); сообщения `build.bat`/`clean.bat` и скрипты `tools\*.ps1` — **только ASCII**. Причина: cmd.exe ненадёжно выводит UTF-8 из bat-файла, а Windows PowerShell 5.1 читает `.ps1` без BOM как ANSI и падает на кириллице.
* Проверки после сборки: `tests\smoke.bat` (контракт CLI и коды возврата), `powershell -File tools\check_exe.ps1` (обе иконки и манифест внутри exe), `powershell -File tools\check_task_xml.ps1` (XML задач `AutoSave`/`AutoRestore`: BOM, схема, principal, триггеры из `Config.ini`, команда; с ключом `-Register` дополнительно проверяет, что Планировщик этот XML принимает, и сразу снимает временную задачу).
  `smoke.bat` копирует exe в `%TEMP%\screenmemory-smoke` и работает там: программа держит `layout.txt`/`admin.log` рядом с собой, поэтому `save` из теста не должен затирать рабочий слепок в `bin\` (иначе теряются эталоны — CONTEXT п. 54).

## 6. Формат файла `bin\layout.txt`

Обычный текст, UTF-8 (без BOM в записи, с допуском BOM при чтении), CRLF. INI-подобный: секции `[...]`, строки `ключ=значение`; разделитель — первый `=`. Своя реализация чтения/записи (WinAPI-профили не умеют UTF-8). Экранирование: `\n`, `\r`, `\\`, `\;` для значений с переводами строк (заголовки окон бывают многострочными).

```
# ScreenMemory layout v1
# saved=2026-11-12T21:15:03  screen=7680x2160  monitors=2  desktops=4  windows=17
[desktop.0]
guid={3BBD80D8-D12B-4B44-AC94-2579E6984975}
name=Работа
[desktop.1]
guid={09D112DA-0BB6-4073-8A33-63EFF448696E}
name=AliExpress
[desktop.2]
guid={D7B24E7A-F0FF-435E-BA53-55D2EFDC7A32}
name=Game
[desktop.3]
guid={4AD61A74-9B8C-4F97-AFC3-C09DDC97FF33}
name=ESP32

[monitor.0]
device=\\.\DISPLAY4
rect=0,0,3840,2160        ; положение монитора на момент сохранения
work=0,0,3840,2120        ; рабочая область (без панели задач)
dpi=96
primary=1
[monitor.1]
device=\\.\DISPLAY1
rect=3840,0,7680,2160
work=3840,0,7680,2120
dpi=96
primary=0

[window.0]
desktop=1                ; индекс десктопа из списка выше
desktop_name=AliExpress   ; имя десктопа на момент сохранения (пусто = без имени)
pinned=0                 ; 1 = «показывать на всех рабочих столах»
zg=0                     ; z-order, 0 = самое верхнее в своём десктопе
exe=C:\Windows\explorer.exe
cmdline=C:\Windows\explorer.exe "C:\Projects"
url=https://ikrut.pro/Water2/  ; только окна браузеров: адрес активной вкладки (UIA)
class=CabinetWClass
folder=C:\Projects       ; только для Проводника
title=Projects
aumid=                   ; AUMID: у UWP и pinned-приложений; у обычных Win32 пусто
monitor=\\.\DISPLAY4      ; якорь относительных координат
mrel=120,140,1360,760     ; ОСНОВНОЕ: left,top,right,bottom ОТНОСИТЕЛЬНО угла своего монитора
rect=120,140,1360,760     ; абсолютные координаты на момент сохранения (для сверки/диагностики)
frame=124,144,1356,756    ; EXTENDED_FRAME_BOUNDS, только для диагностики
show=normal               ; normal | maximized | minimized
uwp=0
elevated=1               ; 1 = окно было открыто от администратора (0.9.3, §9.3)
```

Правила:

* Секция `[desktop.N]` — полный список десктопов на момент сохранения, индексы = порядок из `VirtualDesktopIDs`.
* `[window.N]` — по одному на окно; `desktop` — индекс, `desktop_name` — имя (главный ключ при восстановлении).
* `url` — адрес активной вкладки окна браузера (Chrome, Edge, Firefox, Opera, Brave, Vivaldi, Яндекс, IE). В командной строке процесса его нет: адрес живёт в профиле, поэтому он читается через UI Automation при `save` (CONTEXT п. 58). Ключ пишется только для окон браузеров и только когда адрес прочитан. Нужен фазе B: запуск браузера без адреса открыл бы пустое окно/чужую вкладку, поэтому такая запись не перезапускается, а попадает в `admin.log` (§9.3).
* `pinned=1` — окно пишется **один раз** (не по разу на десктоп), координаты берутся с того десктопа, где оно было видно.
* `aumid` нужен для UWP (запуск через `ActivateApplication`) и для сопоставления с `PinnedApps`, где вместо пути к exe лежит AUMID. Необязательные ключи (`cmdline`, `folder`, `aumid`, `frame`) пишутся только когда значение есть.
* Секция `[monitor.N]` — конфигурация мониторов на момент сохранения (устройство, положение, рабочая область, DPI). Индекс `N` = тот, что отдаёт `EnumDisplayMonitors`.
* Координаты окна хранятся **дважды**: `mrel` — относительно левого-верхнего угла своего монитора (основное), `rect` — абсолютные (для сверки). Восстановление идёт от монитора-якоря (`monitor=`), а не от абсолютных координат экрана.
* `elevated=1` — окно было открыто процессом с повышенными правами: `GetTokenInformation(TokenElevation)` у PID этого окна вернул `TokenIsElevated != 0` (`src\process_info.cpp`: `ProcessElevation`), см. §9.3. Ключ пишется всегда (0 тоже), потому что при восстановлении от него зависит, каким токеном запускать приложение. Файлы без ключа читаются как `elevated=0` — старые слепки остаются годными.
* Неизвестные ключи при чтении игнорируются (прямая совместимость с правками руками). Пустые секции `[window.N]` — дырка в нумерации после такой правки — тоже выбрасываются: у настоящей записи всегда есть чем опознать окно (`exe`, AUMID, заголовок или класс), а пустая запись иначе попадала в отчёт как «не запускаем: команду запуска собрать не удалось» (CONTEXT п. 72).

### 6.1 Рабочие версии и защищённые копии (0.9.1)

В `bin` рядом с `layout.txt` лежат две цепочки копий с разным хозяином:

```
layout.txt                            текущий слепок
layout-YYYY-MM-DD_HH-MM-SS.txt        рабочие версии, по умолчанию 3 (ключ Layouts)
layout-вчерашний-день.txt             ┐
layout-позавчерашний-день.txt         ├ цепочка дней: двигает restore
layout-позапозавчерашний-день.txt     ┘
layout-прежняя-конфигурация.txt       ┐
layout-прежняя-конфигурация-2.txt     ├ цепочка конфигураций: двигает save
layout-прежняя-конфигурация-3.txt     ┘
```

Во всех трёх копиях лежит обычный слепок (тот же формат §6), поэтому любая из них годится
для `restore --from`.

**`save` — рабочие версии и смена конфигурации:**

1. Собираем содержимое в памяти → пишем `layout.new` (атомарность).
2. Читаем прежний `layout.txt`. Если конфигурация изменилась — другой состав или геометрия
   мониторов, другой набор GUID десктопов — прежний слепок копируется в
   `layout-прежняя-конфигурация.txt`, прежние копии сдвигаются (`-2` → `-3`, `-3`
   удаляется). Имена десктопов и порядок вывода мониторов изменением **не** считаются.
   Зачем: при сбое мониторы на время пропадают (остаётся один), `save` по задаче AutoSave
   тут же записывает искажённый слепок, и «как было при четырёх мониторах» иначе не
   восстановить. Копия делается **до** ротации — после неё `layout.txt` это уже новый
   слепок. Три места в цепочке страхуют от того, что «прежним» окажется слепок, снятый
   уже после сбоя.
3. Если `layout.txt` существует → переименовываем в `layout-<время существующего файла>.txt`
   (время из его заголовка `# saved=`, иначе из mtime).
4. `layout.new` → `layout.txt` через `MoveFileExW(..., MOVEFILE_REPLACE_EXISTING)`.
5. Чистка: из рабочих версий оставляем `Layouts` самых новых (по умолчанию 3, допустимо
   1…20). Рабочая версия узнаётся по имени (`IsVersionName`: `layout-` + метка времени +
   `.txt`), поэтому защищённые копии не считаются и не удаляются никогда — даже при
   `Layouts=1`.

**`restore` — цепочка дней (это и есть «началась новая сессия»):**

1. Читаем `layout.txt` (или файл из `--from`).
2. Если `--from` не задан и это не `--dry-run`: этот слепок копируется в
   `layout-вчерашний-день.txt`, прежний «вчерашний» переезжает в «позавчерашний»,
   «позавчерашний» — в «позапозавчерашний», «позапозавчерашний» удаляется.
3. Цепочка **не** двигается, если:
   * тот же слепок (метка `# saved=`) уже лежит во «вчерашнем дне» — иначе три ручных
     `restore` подряд съели бы всю историю;
   * слепок снят **после** текущей загрузки системы — перезагрузки не было, это середина
     сессии. Ориентир здесь не время суток, а факт загрузки (`NtQuerySystemInformation`,
     `SystemTimeOfDayInformation`): вчерашний слепок снят до неё, поэтому восстанавливаемся
     «из вчера» и тогда, когда перезагрузка случилась в 16:00;
   * задан `--from` — это осознанный откат, а не начало дня.

Реализация (`src\storage.cpp`): имя ротации берётся из заголовка `# saved=` предыдущего
файла (а не из времени переименования — иначе после долгого простоя дата в имени врала бы);
если эта секунда уже занята (быстрые повторные `save`), к имени добавляется `-1`, `-2`, …
Сортировка версий для чистки — по `ftLastWriteTime`, потому что суффикс `-N` ломает
лексикографический порядок. Если переименование старого файла не удалось (файл занят
антивирусом), `save` не падает: свежий слепок всё равно заменяет `layout.txt`, в консоль
идёт предупреждение.

Откат теперь без переименований: `ScreenMemory.exe restore --from layout-вчерашний-день.txt`
(или любой `layout-<время>.txt`, `layout-прежняя-конфигурация.txt`); ключ принимает и
абсолютный путь. Ручное редактирование `layout.txt` и запуск `restore` тоже работают.

## 7. Алгоритм `save`

1. `CoInitializeEx(COINIT_APARTMENTTHREADED)`; читаем список десктопов (GUID, имя, индекс) из реестра и набор pinned-приложений из `PinnedApps`. **Количество десктопов и их имена не предполагаются заранее** — берём ровно то, что есть сейчас (1, 4, 10 — сколько угодно), имена могут отсутствовать, повторяться и быть любыми.
2. Определяем текущий десктоп: `GetForegroundWindow()` → `IVirtualDesktopManager::GetWindowDesktopId`; если GUID пустой — берём GUID первого окна без cloaking.
3. `EnumWindows` + фильтры кандидатов:
   * `IsWindowVisible(hwnd)` = true;
   * `GetWindow(hwnd, GW_OWNER)` == NULL (не owned-окна) — исключение: диалоги класса `#32770` с непустым заголовком берём;
   * нет `WS_EX_TOOLWINDOW`;
   * не наш собственный процесс, PID != 0;
   * непустой заголовок (`GetWindowTextLengthW > 0`) либо класс из whitelist (`CabinetWClass`, `ExploreWClass`, `ApplicationFrameWindow`, `#32770`);
   * не пустая UWP-рамка: `ApplicationFrameWindow` без заголовка берём только если внутри есть `Windows.UI.Core.CoreWindow`; рамка без содержимого — пустышка, которую Explorer держит по одной на монитор (проверено на этой машине: две такие рамки, `pid` = `explorer.exe`, дети — только `ApplicationFrameTitleBarWindow` и `ApplicationFrameInputSinkWindow`);
   * чёрный список классов: `Progman`, `WorkerW`, `Shell_TrayWnd`, `Shell_SecondaryTrayWnd`, `Windows.UI.Core.CoreWindow`, `ApplicationManager_DesktopShellWindow`, `MultitaskingViewFrame`, `ForegroundStaging`, `XamlExplorerHostIslandWindow`, `TaskListThumbnailWnd`, `Windows.Internal.Shell.TabProxyWindow`, `DV2ControlHost`, `MsgrIMEWindowClass`.
4. **Ключевой момент — окна на других десктопах.** `EnumWindows` возвращает их все; на неактивных десктопах окна «закрыты» (cloaked) оболочкой. Проверяем `DwmGetWindowAttribute(hwnd, DWMWA_CLOAKED, ...)`:
   * `DWM_CLOAKED_SHELL (2)` → окно на другом виртуальном десктопе → **сохраняем** (основная задача);
   * `DWM_CLOAKED_APP (1)` → UWP в suspended → сохраняем, помечаем `uwp=1`;
   * `DWM_CLOAKED_INHERITED (4)` → служебное/унаследованное → пропускаем.
5. Для каждого окна собираем:
   * `GetWindowPlacement` → `showCmd` (normal/maximized/minimized) и `rcNormalPosition` → `rect`;
   * `DwmGetWindowAttribute(DWMWA_EXTENDED_FRAME_BOUNDS)` → `frame` (видимые границы, для clamp/диагностики);
   * класс (`GetClassNameW`), заголовок (`GetWindowTextW`), стили;
   * exe: `GetWindowThreadProcessId` + `OpenProcess(PROCESS_QUERY_LIMITED_INFORMATION)` + `QueryFullProcessImageNameW`;
   * командная строка: `NtQueryInformationProcess(ProcessCommandLineInformation)` (через `GetProcAddress` из ntdll, без жёсткой линковки) — нужна, чтобы перезапустить приложение с его аргументами; fallback — только путь exe;
   * AppUserModelID: `SHGetPropertyStoreForWindow` → `PKEY_AppUserModel_ID` (нужен для сопоставления с `PinnedApps` и для UWP);
   * десктоп: `IVirtualDesktopManager::GetWindowDesktopId` → GUID → индекс по списку из п. 2.1 (+ имя); если GUID не получен — текущий десктоп. У pinned-окон GUID **не** найдётся в `VirtualDesktopIDs`: это маркер «окно на всех столах» (проверено: `{BB64D5B7-…}` для всех 6 pinned-окон этой машины), такие окна помечаем `pinned=1` и между десктопами не переносим;
   * `pinned`: путь exe (или AUMID) найден в `PinnedApps` (сравнение без учёта регистра) → 1;
   * для `CabinetWClass`/`ExploreWClass` — `folder` (путь папки, см. п. 9.2);
   * монитор-якорь: `MonitorFromWindow(hwnd, MONITOR_DEFAULTTONEAREST)` → `GetMonitorInfoW` (`szDevice`, `rcMonitor`, `rcWork`); считаем `mrel = rcNormalPosition - rcMonitor.topleft`; DPI монитора — `GetDpiForMonitor`; полный список мониторов (`EnumDisplayMonitors`) один раз на весь слепок пишем в секции `[monitor.N]`.
6. Порядок в файле: сначала по десктопу (индекс), внутри — сверху вниз по z-order, полученному обходом `GetWindow(hwnd, GW_HWNDNEXT)` от вершины (`GetTopWindow`). Поле `zg` = номер от вершины внутри своего десктопа.
7. Дедупликация: pinned-окно пишется один раз; записи с одинаковыми `(exe, class, title, desktop)` и почти равными `rect` (±8 px) считаем дублем и пишем один раз.
8. Запись по правилам п. 6.1 (атомарно, защищённая копия при смене конфигурации, рабочие версии), в консоль — краткий итог: сколько окон/десктопов, путь файла.

## 8. Алгоритм `restore`

### 8.0 Чтение и маппинг десктопов (без хардкода имён)

1. Читаем файл `layout.txt` из папки с exe (ключ `restore --from <файл>` читает любой другой слепок: рабочую версию, «вчерашний день», «прежнюю конфигурацию» — это и есть откат, §6.1). Проверяем заголовок `# ScreenMemory layout v1`; неизвестные ключи игнорируем.
2. Читаем актуальный список десктопов из реестра. Для каждого сохранённого десктопа ищем цель в порядке приоритета **имя → номер → GUID** (CONTEXT п. 57):
   1. **имя** (`desktop_name` не пусто и совпадает с именем существующего десктопа, без учёта регистра и крайних пробелов) — главный признак: человек, назначая имя, связывает десктоп с тем, что на нём открыто, и это важнее любого GUID. Заодно покрывает случай «десктоп удалили и создали заново с тем же именем». Если имён-дублей несколько — берём ближайший по индексу и отмечаем в отчёте `ambiguous-name`;
   2. **номер (индекс)** — если десктопа с сохранённым именем нет (или у записи имени нет), берём тот же номер: пользователь, переставляя десктопы в Task View, помнит «третий слева», а не GUID. В отчёте `по: индекс` + пометка «имени нет в системе»;
   3. **GUID** — последний по важности: он переживает переименование, но ничего не говорит о том, что на десктопе было открыто. Используется, когда номера в системе уже нет;
   4. **первый десктоп текущего списка (индекс 0)** — если ничего не нашлось. Это «нулевой десктоп» из требования 15, **не** десктоп с именем «Работа»: имя не хардкодится. В отчёте `fallback`.
3. Строим карту `индекс из файла → GUID текущего десктопа` (+ отметки `renamed`, `name-not-found`, `ambiguous-name`, `fallback` для отчёта).
4. Устойчивость к изменениям набора десктопов:
   * десктопов стало **больше** → новые просто не используются, окна на них не претендуют;
   * десктопов стало **меньше** / сохранённый удалён → его окна идут на десктоп 0 с сохранёнными координатами;
   * десктоп **переименован** → имя не совпало, номер занят тем же десктопом → окна возвращаются на него же (в отчёте `по: индекс`, `renamed`, если GUID тот же);
   * десктоп **переставлен** в Task View → срабатывает имя (или номер), порядок не важен;
   * у десктопа **нет имени** → работаем по номеру, при неудаче — по GUID;
   * у записи есть имя, а десктопа с таким именем нет и номер занят → в отчёте «имени нет в системе».
5. Скрытый отладочный ключ `--dry-run` — печатает карту десктопов (файл → текущий, с пометками) и план действий по каждому окну (текущая нормальная позиция → целевая, стол, состояние, перенос/`pinned`, поправки `dpi`/`primary`/`size`/`off-screen`), ничего не меняя.

### 8.1 Снимок текущих окон и матчинг

Собираем текущие окна тем же фильтром, что в `save` (без записи в файл). Сопоставление «запись ↔ окно» — жадное по убыванию score, каждое окно и каждая запись используются один раз:

| Признак | Баллы |
|---|---|
| exe совпал (путь, без учёта регистра) | +100 |
| class совпал | +50 |
| title совпал точно | +40 |
| `folder` Проводника совпал | +40 |
| AUMID совпал (UWP: exe у всех `ApplicationFrameHost.exe`) | +60 |
| `url` совпал (адрес вкладки браузера, §8.3 п.2) | +60 |
| desktop: GUID совпал | +25 |
| desktop: только имя совпало | +10 |
| rect близок (пересечение ≥ 50 %) | +20 |

Порог принятия — 100 (exe совпал) либо 90 для Проводника (`class` + `folder`). Совпадение десктопа — только разрешение ничьих, «угадывать окно» по десктопу нельзя. Не сопоставленные записи идут в фазу B.

Два правила, добавленные при реализации (`matching.cpp`, CONTEXT п. 44): **вето по `folder`** — если и в записи, и у живого окна папка известна и они разные, пара не рассматривается вовсе (лучше не восстановить окно, чем утащить чужое окно Проводника на его место); **вето по AUMID** — по той же причине для UWP-рамок.

> Третье вето — **по адресу страницы** (0.8.3, CONTEXT п. 60): `restore` читает адрес активной вкладки у живых окон браузеров (UIA, только если в слепке есть браузерные записи с `url=`; неудачное чтение повторяется — время не критично), и если адрес известен и у записи, и у окна, но разный — пара не создаётся. Запись уходит в фазу B и открывает нужную страницу отдельным окном, а чужое окно остаётся где было; совпадение адреса даёт +60 и признак `url` в `--verbose`. Так закрыт случай CONTEXT п. 55, когда запись вкладки Chrome «прилипала» к окну с другим содержимым по баллам `exe`+`class`+`aumid` (210) и утаскивала его на чужой десктоп. Если адрес у окна прочитать не удалось, работает прежний порог: адрес известен только у записи — пара принимается по `exe`, бонуса нет.

> Четвёртое правило — **неоднозначность на разных десктопах** (0.8.3, CONTEXT п. 61; требование пользователя: окна одного приложения, открытые одновременно на разных столах, не должны перепутываться). Если у записи несколько окон с одинаковым максимальным баллом, эти окна находятся на разных десктопах, а известные признаки (`exe`, `class`, `title`, `folder`, `aumid`, `url`) их не различают, то выбор пары решает, какое окно куда поедет, — при нехватке данных это лотерея. Такие кандидаты отклоняются: запись уходит в фазу B (приложение откроет себе отдельное окно), живые окна остаются на своих местах, а в отчёте появляется строка «неоднозначно: N записей…» (`MatchStats::ambiguous`). Если окна на одном десктопе или полностью неотличимы по всем известным признакам, правило не срабатывает: перепутывание ничего не меняет и переносов не добавляет. Правило работает только на разрешение ничьих — сами баллы не меняются.

### 8.2 Фаза A — расставить существующие окна

Для каждой пары (запись, hwnd):

1. Если окно свёрнуто (`IsIconic`) — `ShowWindow(hwnd, SW_RESTORE)`.
2. Геометрия через `SetWindowPlacement` (единственный корректный путь для maximized/minimized: `rcNormalPosition` = `mrel`, пересчитанный в абсолютные координаты по п. 8.4; `showCmd` = `SW_SHOWNORMAL` / `SW_SHOWMAXIMIZED` / `SW_SHOWMINIMIZED`).
3. Pinned-окна (`pinned=1`) **не переносим на другой десктоп** (они видны везде, `MoveWindowToDesktop` для них не работает) — только геометрия.
4. Обычные окна — перенос на целевой десктоп **двумя путями** (0.8.1): сначала внутренний
   `IVirtualDesktopManagerInternal::MoveViewToDesktop` по `IApplicationView` окна (работает для
   окон **любого** процесса), при недоступности внутреннего интерфейса — документированный
   `IVirtualDesktopManager::MoveWindowToDesktop` (он переносит только окна своего процесса).
   Если целевой десктоп и так текущий — вызов не нужен.
5. Успех COM-вызова — **не** доказательство переноса: десктоп окна перечитывается
   (`GetWindowDesktopId`), при расхождении — до трёх попыток с паузой 400 мс, дальше строка
   `move-desktop-failed` в `admin.log` и честный счётчик в отчёте.
6. Скрытый отладочный ключ `--dry-run` — только логирование: план печатается теми же функциями, что применяют изменения, поэтому «что было бы сделано» совпадает с тем, что будет сделано.

> Документированный `IVirtualDesktopManager::MoveWindowToDesktop` для окна **чужого** процесса
> возвращает `E_ACCESSDENIED` даже при переносе на текущий десктоп (проверено экспериментом
> на Win10 22H2: блокнот, `explorer.exe`, свой процесс — 0.8.1), поэтому в 0.8.0 окна чужих
> процессов фактически никогда не уезжали на сохранённый десктоп, хотя отчёт считал перенос
> выполненным. Внутренний путь (`CLSID_ImmersiveShell` → `QueryService(SID_IVirtualDesktopManagerInternal)`
> + `IApplicationViewCollection::GetViewForHwnd`) — единственный способ перенести чужое окно.
> Раскладка его vtable недокументирована, поэтому перед первым переносом выполняется самопроверка
> (см. §9.1).

### 8.3 Фаза B — запуск отсутствующих приложений (всегда включена)

0. **Окна открывает не только `restore` (0.9.2, CONTEXT п. 69).** После входа в систему одновременно с `restore` работают Windows (возврат окон папок при `PersistBrowsers=1`, приложения из автозагрузки) и браузер (сессия профиля). Снимок для фазы A делается один раз, поэтому запись, чьё окно появилось позже, остаётся без пары, и фаза B запускает вторую копию. Две меры: (а) перед фазой B ждём «успокоения» — пока состав верхнеуровневых окон меняется, запускать нельзя; ждём тишины 2 с, но не дольше `settle-wait` секунд (ключ `Config.ini`, по умолчанию 10, 0 — не ждать, максимум 600), потому что система может «сыпать» окнами бесконечно; (б) перед **каждым** запуском запись перепроверяется `MatchRecord` — те же правила §8.1, что в фазе A, но против окон, которые ещё ничьи. Найденное окно ставится на место общим кодом фазы B, второй экземпляр приложения не запускается; в отчёте — строка «уже открыто: …» и итог «Уже было открыто (запускать не понадобилось): N». `--dry-run` ничего не ждёт и перепроверку не выполняет: он ничего не меняет.
1. Пропускаем записи, для которых окно найдено в фазе A, и записи `pinned=1`, если такой exe уже запущен (иначе получим дубли).
2. Команда запуска:
   * Проводник (`folder` не пусто) → `explorer.exe "<folder>"`;
   * UWP (`uwp=1` и есть AUMID) → `IApplicationActivationManager::ActivateApplication(aumid)`, fallback — `cmdline`;
   * браузер (Chrome, Edge, Firefox, Opera, Brave, Vivaldi, Яндекс, IE) → `"<exe>" --new-window "<url>"` (`-new-window` у Firefox, без ключа у IE): адреса страницы в `cmdline` нет, он берётся из поля `url`; запись без `url` **не** запускается — иначе открылось бы пустое окно (в отчёт `browser-no-url`, а в `admin.log` попадает команда без адреса);
   * остальное → `cmdline`, если начинается с существующего пути, иначе `exe`.
3. `CreateProcessW`: консольной программе (`IMAGE_SUBSYSTEM_WINDOWS_CUI`, определяется по заголовку PE — `IsConsoleImage`) — `CREATE_NEW_CONSOLE`, графической — `CREATE_NO_WINDOW` (CONTEXT п. 70): иначе дочерний процесс наследует консоль `restore`, получает `CTRL_CLOSE_EVENT` вместе с ней и пишет в наш журнал. Затем ожидание окна: poll каждые 250 мс, таймаут **60 с** (константа `kLaunchTimeoutMs`), поиск по PID и/или (class + title). Ожидание прекращается досрочно, только если процесс завершился (упал или сразу закрылся) — тогда причиной будет `launch-failed`, а не `launch-timeout`. Если `CreateProcessW` вернул `ERROR_ELEVATION_REQUIRED` — пишем строку в `admin.log` и идём дальше.
4. Геометрию и перенос на десктоп ставим **не сразу после появления окна**, а когда все запуски уже сделаны и окна «успокоились»: часть приложений (nw.js — AudioPL) сама ставит своё окно после старта и переигрывает наш `SetWindowPos`. Поэтому фаза B идёт тремя проходами: (а) запустить все планы, запомнив PID и окна «до запуска»; (б) дождаться окон (`WaitForWindow`, у браузеров — `WaitForBrowserWindow` с подтверждением страницы и закрытием пустых окон); (в) `WaitRectsStable` — ждать, пока прямоугольники перестанут меняться (два одинаковых опроса подряд, шаг 500 мс, тишина 2 с, не дольше 12 с) — и только затем `ApplyMatch` для всех. `WaitForWindow` получает `otherPids`, чтобы не забрать окно соседнего запуска того же приложения (две записи одного exe иначе менялись окнами).
5. Браузер: перед переносом ждём подтверждения страницы — `WaitForBrowserPage` опрашивает адресную строку (шаг 500 мс, до 30 с, `kBrowserReadyTimeoutMs`) и считает окно готовым, когда адрес непустой и не меняется между двумя опросами. Chrome/Edge показывают окно раньше, чем открывают страницу, и тащить окно в момент навигации — самое «спешное» действие; если адрес так и не подтвердился, окно всё равно ставим на место (иначе оно останется посреди экрана), но факт пишем в `Trace`. Если окна нет вовсе (п. 3) — в отчёт `launch-timeout`.
6. Браузер, который восстанавливает сессию профиля (Firefox), при **холодном** старте (CONTEXT п. 63): (а) если exe ещё не запущен, перед запуском его поднимают без аргументов и ждут окно + 2.5 с (`WarmUpBrowser`) — иначе `-new-window <url>` открывает адрес вкладкой в восстановленном окне, а не отдельным окном; (б) окно ищется **по адресу страницы** (`WaitForBrowserWindow`, 20 с, `kBrowserWindowTimeoutMs`), а не «первое новое окно класса»: у Firefox окно создаёт уже работающий процесс, и окно восстановленной сессии того же класса иначе принимается за новое; (в) после `WaitForBrowserPage` закрываются пустые окна браузера, появившиеся после запуска (`CloseEmptyBrowserWindows`: `about:`-страницы и окна со стартовым заголовком без адреса, кроме нашего рабочего, 4 попытки по 700 мс). Само окно восстановленной сессии не закрывается и не переносится — в нём вкладки пользователя.

### 8.4 Координаты: относительные от монитора + clamp

Почему не абсолютные: окно живёт в координатах «виртуального экрана», где у primary-монитора угол всегда (0,0), а остальные мониторы получают смещения по раскладке из параметров экрана. Достаточно поменять мониторы местами, сменить primary, поменять разрешение или отключить монитор — и все сохранённые абсолютные координаты указывают уже в другие места, хотя пользователь ничего не двигал. Поэтому якорь — конкретный монитор, а координаты — от его угла.

Алгоритм восстановления позиции:

1. Берём `monitor` (например `\\.\DISPLAY4`) и `mrel` (left, top, right, bottom относительно угла этого монитора).
2. Ищем живой монитор с тем же device-именем (`EnumDisplayMonitors` + `GetMonitorInfoW().szDevice`):
   * **найден** → `x = cur_monitor.left + mrel.left`, `y = cur_monitor.top + mrel.top`, размер из `mrel`. Результат не зависит от того, сдвинулась раскладка или нет;
   * **не найден** (монитор отключён/переназначен) → пробуем абсолютные `rect`: если область пересекается с живым монитором — используем её; иначе переносим на primary, сохраняя относительную позицию и не увеличивая размер.
   * `monitor` пуст (на `save` не удалось получить `GetMonitorInfoW`) → в `mrel` записаны абсолютные координаты, поэтому для такой записи сразу берём `rect`.
3. Если `dpi` монитора изменился (например 96 → 120) — пересчитываем `mrel` на коэффициент, иначе окно «уползёт» на десятки пикселей.
4. `clamp`: если окно всё же вышло за `SM_XVIRTUALSCREEN`/`SM_CXVIRTUALSCREEN` — прижимаем внутрь ближайшего монитора (`MonitorFromRect`), размер ограничиваем рабочей областью (`work`, а не полным `rect`, чтобы не залезать под панель задач).
5. Кросс-мониторные окна не масштабируем, только сдвигаем.
6. На `save` симметрично: `mrel = rect - monitor_rect.topleft` по монитору, который отдаёт `MonitorFromWindow(hwnd)` (для maximized — по `rcNormalPosition`).

### 8.5 Фаза C — z-order внутри десктопа

Для каждого десктопа берём записи с `zg` по убыванию и поднимаем окна: `SetWindowPos(hwnd, HWND_TOP, 0,0,0,0, SWP_NOMOVE|SWP_NOSIZE|SWP_NOACTIVATE)`. `SetForegroundWindow` не используем, чтобы не воровать фокус.

### 8.6 Отчёт и коды возврата

Печатаем: десктопов в файле/найдено, окон в файле, `restored`, `moved-desktop`, `launched`, `fallback-desktop`, `skipped` (с причиной), `errors`. Коды: `0` — всё ок, `1` — частично (в том числе окна на десктопе 0 из-за отсутствующих десктопов), `2` — файл не найден/битый, `3` — не удалось получить список десктопов.

> Реализовано на этапе 6 (0.6.0): печатаются карта десктопов («по GUID / по имени / по индексу / fallback», с пометками `переименован` и `имя не уникально`), строка «окна: в файле N, живых M, сопоставлено K», итог «применено / перенесено на другой десктоп / z-order выставлен», «нет живого окна: N — их запуск появится на этапе 7 (фаза B)» и «не удалось применить: N». `launched` и `fallback-desktop` появятся вместе с фазой B и отчётом этапа 8. В `--verbose` печатается каждая принятая пара с баллами и признаками (`exe class title folder aumid desktop rect`), а каждое предупреждение о неудаче содержит причину (`SetWindowPlacement: 5: Отказано в доступе`).

> Реализовано на этапе 8 (0.8.0): добавлен отдельный счётчик окон, которые в итоге оказались на десктопе 0, потому что их сохранённого десктопа в системе нет (`fallback-desktop`). В реальном прогоне печатается «Оказалось на десктопе 0 (целевой десктоп не найден): N» и предупреждение «окон на десктопе 0: N — сохранённых десктопов нет в системе; пересохраните раскладку после возврата десктопов»; в `--dry-run` — «уехало бы на десктоп 0 …: N». Счётчик не включает pinned-окна (они видны на всех десктопах и никуда не уезжают) и окна, которые применить не удалось (они попадают в `errors`). Проверено сценарием «целевой десктоп исчез»: у `[desktop.0]` в `layout.txt` подменяются `guid` и `name`, `restore` даёт `fallback 1` в карте, «Оказалось на десктопе 0 …: 27» (все непривязанные окна этого стола; pinned исключены) и код возврата `1`; в `--dry-run` — «уехало бы на десктоп 0 …: 27». Окна при этом не двигаются, потому что fallback указывает на тот же первый десктоп.

> Реализовано на этапе 7 (0.7.0): строка «нет живого окна: N» заменена фазой B, поэтому печатается «Запущено: N, не удалось поднять: M, не запускается: K» (например `Запущено: 2, не удалось поднять: 0, не запускается: 0`), а в `--dry-run` — «было бы запущено: N, не запускается: K». Записи, которые не перезапускаются (консоль, нет команды) и окна, которые не удалось поднять, попадают в `bin\admin.log`; если журнал пополнился, печатается «требуют вмешательства человека: N — открываю …». Отдельная строка `fallback-desktop` (счётчик окон, уехавших на десктоп 0 из-за отсутствия их десктопа) сделана на этапе 8 — см. абзац выше.

> Пиновать окна программой (`PinWindow`) не планируем: приложения уже помечены в `PinnedApps`, Explorer применит признак сам. Если окно потеряло pin — лечится один раз вручную в Task View; при необходимости позже добавим недокументированный `IVirtualDesktopPinnedApps` отдельной опцией.

### 8.7 Предварительный шаг: внешняя программа из Config.ini (0.8.5)

Второй монитор на этой машине — телевизор: он включается позже компьютера, и рабочий стол на него не приходит, пока раскладку не поправит сторонняя программа (`MultiMonitorTool.exe`). Поэтому настоящий `restore` начинается с предварительного шага: если в `Config.ini` рядом с exe задан ключ `prelaunch`, эта программа запускается, и работа ждёт, пока пользователь не закроет её окно. `save` шаг не выполняет: он ничего не восстанавливает, а только записывает то, что видно сейчас (требование пользователя, 16.11.2026).

Файл и формат. `Config.ini` необязателен; читается `src\config.cpp` при каждом запуске (UTF-8 с BOM и без, UTF-16LE с BOM, откат на системную ANSI; `;` и `#` — комментарии, секции `[...]` допускаются, значения разворачиваются как переменные среды; незнакомые ключи не мешают — в `--verbose` они попадают в лог). Ключи: `prelaunch=<путь к программе>`, `prelaunch-args=<аргументы>`, `prelaunch-timeout=<секунды>` (`0` — ждать без ограничения).

Ожидание (`sm::RunPreLaunch`, `src\launcher.cpp`): опрос 250 мс; «окно закрыто» = видимых окон этой программы не осталось (процесс может остаться в памяти) либо процесс завершился, не показав окна (безоконной утилите даётся 3 с на появление окна «дочерней» копии). Окна считаются по пути exe, а не по PID: утилита может показать окно из уже запущенного процесса, а свой завершить. Пока окно открыто, `restore` работу не начинает — иначе раскладка применяется к «недонастроенному» экрану.

Отказы работу не блокируют: пустой `prelaunch`, программа не найдена, `CreateProcessW` не смог стартовать, истёк `prelaunch-timeout` — печатается предупреждение, и работа продолжается (после сбоя утилиты пользователь не должен остаться без восстановления вовсе). `--dry-run`, `--list`, `--help` и `--version` предварительный шаг не запускают: они ничего не меняют; `save` — тоже, он только записывает то, что видно сейчас (см. выше).

## 9. Технические детали

### 9.0 Cloaking — что значит «окно закрыто оболочкой»

Речь не о закрытии окна, а о механизме **DWM cloaking** («накрыть плащом»): композитор рабочего стола (Desktop Window Manager) исключает окно из отрисовки, но само окно продолжает жить — у него есть HWND, он есть в списке окон, `IsWindowVisible()` возвращает `TRUE`, сообщения окно получает. Просто DWM его не рисует и пользователь его не видит.

Зачем это нужно Windows: именно так реализованы виртуальные рабочие столы и приостановка UWP-приложений. Окно на неактивном десктопе не уничтожается и не скрывается через `ShowWindow` — его «накрывает» оболочка (Explorer/Shell). Отсюда флаги, которые возвращает `DwmGetWindowAttribute(hwnd, DWMWA_CLOAKED, ...)`:

| Флаг | Значение | Что это на практике |
|---|---|---|
| `DWM_CLOAKED_APP` = `0x1` | окно накрыло само приложение | UWP-приложение в suspended, приложение, скрывающее окно во время загрузки |
| `DWM_CLOAKED_SHELL` = `0x2` | окно накрыла оболочка | **окно на другом виртуальном рабочем столе** (наш основной случай) |
| `DWM_CLOAKED_INHERITED` = `0x4` | унаследовано | owned/дочерние окна накрытого окна |

Практические следствия для программы:

1. **Нельзя отбрасывать cloaked-окна** — именно они и есть «окна на других десктопах», ради которых всё пишется. Классическая ошибка — отфильтровать их по `IsWindowVisible`/cloaked и получить слепок только текущего десктопа.
2. Признак `0x2` используется как «окно на другом десктопе» и как перекрёстная проверка к документированному `IVirtualDesktopManager::IsWindowOnCurrentVirtualDesktop`.
3. `0x1` — UWP suspended: координаты читаются нормально, но окно может не реагировать на перемещение; помечаем `uwp=1` и обрабатываем осторожно.
4. `0x4` — служебные/owned-окна, в слепок не пишем.
5. Проверка на этой машине — этап 3 (команда `list`): открыть окно на **любом не текущем** десктопе, вернуться на первый и убедиться, что окно видно в перечислении с `cloaked=2` и правильным именем десктопа из реестра. **Выполнено в 0.3.0**: например, окна `ESP32` (20 штук), `AliExpress`, `Game` видны из десктопа 0 с `cloaked=shell`, при этом 30 окон `shell` на 59 кандидатов.

### 9.1 Виртуальные десктопы

* Список десктопов: `HKCU\SOFTWARE\Microsoft\Windows\CurrentVersion\Explorer\VirtualDesktops`
  * `VirtualDesktopIDs` (`REG_BINARY`, 16 байт на десктоп) → порядок + GUID. Разбираем по 16 байт и собираем `GUID` через `memcpy` (формат совпадает с Win32 `GUID`: Data1/Data2/Data3 little-endian, Data4 — как есть).
  * `Desktops\{GUID}\Name` (`REG_SZ`) → имя (значения может не быть).
  * `CurrentVirtualDesktop` (`REG_SZ`) на Win10 22H2 **отсутствует** (проверено: в ключе только `VirtualDesktopIDs`). Поэтому «текущий десктоп» определяется каскадом (см. п. 18 списка решений): окно в фокусе → консольное окно → голосование по окнам → окна оболочки → значение из реестра.
  * Терминалы (ConEmu и подобные) держат собственное окно `VirtualConsoleClass`, у которого может не быть записи в диспетчере десктопов: `GetWindowDesktopId` для него возвращает `0x8002802B` (`TYPE_E_ELEMENTNOTFOUND`). Один отказ не должен означать «не определено» — обязателен резервный способ.
* **Идентичность десктопа — GUID; имя только человекочитаемая метка.** Поэтому:
  * десктопов может быть любое количество (1…N), в файл пишем все, в коде нет ни числа, ни имён;
  * имя может отсутствовать → `name=` пустое, дальше работаем по GUID/индексу;
  * имя могут поменять (переименование в Task View) → GUID тот же, окна остаются на своём десктопе;
  * имена могут повторяться (два десктопа «Game») → при матчинге по имени берём ближайший по индексу и пишем в отчёт `ambiguous-name`;
  * десктопы можно переставлять/добавлять/удалять → порядок в файле «замораживается» на момент `save`, на `restore` он сопоставляется с актуальным по GUID/имени (п. 8.0).
* `PinnedApps` → набор значений; **имя значения** и есть идентификатор приложения (data `REG_DWORD` на этой машине всегда 0, признак «закреплено» = наличие значения). Три формы имён:
  * путь к exe: `E:\VirtualWork\4aciki\exe\Часики64.exe`;
  * AUMID: `Microsoft.VisualStudioCode`, `Telegram.TelegramDesktop.2cb78e44…`;
  * `{GUID известной папки}\относительный\путь`: `{6D809377-6AF0-444B-8957-A3773F02200E}\OpenConnect-GUI\openconnect-gui.exe`, `{D65231B0-B2F1-4857-A4CE-A8E7C6EA7D27}\taskmgr.exe`. Папку подставляем через `SHGetKnownFolderPath`, иначе такой путь не сравнить с реальным путём exe.
* `IVirtualDesktopManager` (документирован, `CLSID_VirtualDesktopManager`, `IID_IVirtualDesktopManager` из `shobjidl_core.h`): `GetWindowDesktopId`, `IsWindowOnCurrentVirtualDesktop` — используются всегда; `MoveWindowToDesktop` — только как резервный путь, потому что переносит лишь окна собственного процесса (`E_ACCESSDENIED` для чужих окон, проверено экспериментом в 0.8.1).
* **Перенос окон чужих процессов — через внутренний интерфейс оболочки** (0.8.1, единственное исключение из правила «недокументированное не трогаем»): `CoCreateInstance(CLSID_ImmersiveShell, …, IID_IServiceProvider)` → `IServiceProvider::QueryService(SID_IVirtualDesktopManagerInternal)` → `MoveViewToDesktop(view, desktop)`, а `IApplicationView` берётся из `IApplicationViewCollection::GetViewForHwnd(hwnd)`. GUID-ы и раскладка vtable сверены с открытым проектом M. Scholtes `VirtualDesktop` (Win10 1809–22H2), вызовы идут по индексу слота (`VtableSlot<Fn>`), а не через «фальшивые» объявления интерфейсов — при смене раскладки видно, какой именно слот не совпал.
  Слоты (индекс в **фактической** vtable, где 0 = `QueryInterface`, 1 = `AddRef`, 2 = `Release`): `IServiceProvider::QueryService` = 3; `IApplicationViewCollection::GetViewForHwnd` = 6; `IVirtualDesktopManagerInternal`: `GetCount` = 3, `MoveViewToDesktop` = 4, `GetCurrentDesktop` = 6, `FindDesktop` = 12; `IVirtualDesktop::GetId` = 4. В C#-объявлениях Scholtes нумерация начинается с 0 (CLR сам подставляет три метода `IUnknown`) — если переносить эти индексы в C++ «как есть», вызов слота 0 попадает в `QueryInterface`, и процесс падает с `0xC0000005` внутри `combase.dll` (проверено зондами `probe4`/`probe5`).
* **Запрашивать у `CLSID_ImmersiveShell` надо именно `IID_IServiceProvider`** (`{6D5140C1-7436-11CE-8034-00AA006009FA}`), а не `IID_IUnknown`: объект, отданный как `IUnknown`, имеет в этом процессе другую vtable (слот 3 — не `QueryService`), вызов уходит в рекурсию и роняет процесс stack overflow `0xC00000FD` в `combase.dll` (проверено: `IUnknown` — зависание/падение, `IServiceProvider` — `S_OK`).
* **Самопроверка перед первым использованием** (vtable недокументирован — вызов «не того» слота уронил бы процесс): `GetCount` даёт 1…64, у `GetCurrentDesktop` непустой GUID, и `FindDesktop(этот GUID)` возвращает объект с тем же GUID. Не прошло — внутренний путь недоступен: `причина` печатается один раз в `--verbose`.
* **Несовпадение = остановка работы (0.8.2).** Если раскладка не совпала («чужая сборка Windows»), а перенос окон между десктопами действительно нужен (есть хотя бы одно окно, чей целевой десктоп отличается от текущего, включая окна фазы B, которые появятся на текущем), `restore` **ничего не меняет** и завершается кодом `6` с объяснением: документированный `IVirtualDesktopManager::MoveWindowToDesktop` переносит только окна своего процесса, поэтому «тихий» переход на него оставил бы окна не на своих столах при внешне успешном отчёте. В `--dry-run` печатается тот же диагноз и план, код возврата тоже `6`. Если переносов не требуется (все окна уже на своих столах), несовпадение раскладки ни на что не влияет — работа продолжается.
  * Для проверки этого поведения без реальной несовместимости есть отладочный ключ окружения `SCREENMEMORY_NO_INTERNAL_API=1` — внутренний путь считается недоступным с понятной причиной.
* Объекты (`provider` = `IServiceProvider`, `manager`, `views`) кэшируются на процесс и освобождаются в обратном порядке в `UninitCom()`.
* Остальные недокументированные интерфейсы **не используем**: создание/удаление десктопов, `SwitchDesktop`, `PinWindow` не нужны, потому что при отсутствии десктопа окно уходит на нулевой (требование 15).
* Если `VirtualDesktopIDs` недоступен (политика/будущая версия Windows): fallback — строим список GUID, опрашивая окна через `IVirtualDesktopManager`, индекс = порядок первого появления, имена пустые; в отчёте — предупреждение.

### 9.2 Окна Проводника (одна папка на нескольких десктопах)

* Получаем путь папки для конкретного HWND через `IShellWindows`:
  `CoCreateInstance(CLSID_ShellWindows)` → перебор `IShellWindows::Item(i)` (см. ниже, почему не `FindWindowSW`) → `IWebBrowserApp::get_HWND` = HWND окна → `IShellBrowser::QueryActiveShellView` → `IShellView::QueryInterface(IFolderView2)` → `IPersistFolder2::GetCurFolder` → PIDL → `SHGetNameFromIDList(SIGDN_FILESYSPATH)`.
  Для виртуальных папок (Быстрый доступ, Корзина) файлового пути нет → сохраняем `SIGDN_DESKTOPABSOLUTEPARSING` в `folder` с префиксом `shell:` и восстанавливаем через `explorer.exe "shell:..."`.
* Три грабли, проверенные на Win10 22H2 (19045.6456), — их обходим:
  1. `IShellWindows::FindWindowSW(SWFO_HWND, ...)` возвращает `S_FALSE` вместо окна (проверено на всех окнах Проводника). Поэтому коллекция **перечисляется** через `Item(i)`, а HWND берётся из автоматизационного `IWebBrowserApp::get_HWND` (ровно то, что показывает PowerShell `Shell.Application.Windows().HWND`); запасной вариант — `IShellBrowser::GetWindow` + `GetAncestor(GA_ROOT)`.
  2. `IShellView::GetItemObject(SVGIO_BACKGROUND)` → `IFolderView` отвечает `E_NOINTERFACE`; `IFolderView2` надо спрашивать прямо у `IShellView` через `QueryInterface`.
  3. `IShellBrowser` есть не у всех элементов: на этой машине активное представление отдаёт то сам элемент коллекции, то его `IServiceProvider` → `QueryService(SID_STopLevelBrowser)` — пробуем оба.
* **`IShellWindows` перечисляет только окна активного виртуального стола** (на этой машине — 15 элементов при 34 открытых окнах Проводника), поэтому для окон с других столов есть запасной путь: заголовок окна Проводника — это путь его папки, и он принимается, только если `GetFileAttributesW(title)` подтверждает существующий каталог (`FILE_ATTRIBUTE_DIRECTORY`). У виртуальных папок («Быстрый доступ», библиотеки) заголовок — просто имя, такое окно остаётся без папки, и это честный «папка не определена», а не ошибка.
* Коллекция обходится **один раз за запуск** и складывается в кэш `HWND → папка`: иначе на каждое окно пришлось бы по 15 RPC-вызовов к explorer.exe.
* Матчинг окон Проводника — по `folder`, а не по заголовку (заголовки повторяются).
* Запуск: `explorer.exe "<folder>"`; ожидание нового окна `CabinetWClass` с этим `folder`.
* Нюанс: вкладки Проводника (Win11) не актуальны для Win10, но несколько окон одной папки на разных десктопах — норма, обрабатываем как независимые записи.

### 9.3 Права, elevated-приложения, `admin.log`

* Манифест `asInvoker`, **никаких запусков от администратора**: `explorer.exe`, запущенный с админ-токеном, создаёт отдельный «админский» Explorer, что ломает систему.
* Окна приложений, запущенных от имени администратора, из нашего процесса не перемещаются (UIPI): `SetWindowPlacement`/`SetWindowPos` тихо не срабатывают. Детект: после применения сравниваем фактическое положение с желаемым и смотрим код ошибки `GetLastError() == ERROR_ACCESS_DENIED`.
* `CreateProcessW` для exe с манифестом `requireAdministrator` тоже вернёт `ERROR_ELEVATION_REQUIRED`.
* **Токен выбирается по записи (0.9.3).** Раньше `launcher.cpp` (`RunLaunch`) вызывал `CreateProcessW` без `lpToken`, и Windows создавала дочерний процесс с токеном вызывающего: `restore`, запущенный от администратора (галочка «Запуск от имени администратора» на ярлыке — она живёт в `.lnk`, в реестре её нет), делал администраторскими **все** поднятые приложения, включая `explorer.exe`. Теперь в слепке есть `elevated` (§6), и правило такое:
  * `save` записывает `elevated=1` окнам, чей процесс повышен (`ProcessElevation`);
  * обычный `restore` поднимает `elevated=0` своим (обычным) токеном, а `elevated=1` не поднимает вовсе: запись уходит в `admin.log`, отчёт печатает «не запускаем: … окно было открыто от администратора» и подсказку «запустите restore от имени администратора» (UAC на каждое приложение был бы хуже — N запросов за один `restore`);
  * `restore`, запущенный от администратора, поднимает `elevated=1` своим токеном, а `elevated=0` — **токеном рабочего стола** (`LaunchRights::AsUser`): перед запуском открывается токен `explorer.exe` (`GetShellWindow` → `OpenProcessToken` → `DuplicateTokenEx` → `TokenPrimary`) и процесс создаётся через `CreateProcessAsUser`. Поэтому повышенный `restore` не создаёт второй «админский» Проводник, браузер видит профиль пользователя, UWP активируется, а окна, открытые от администратора, всё равно поднимаются администраторскими — разделение прав получается без UAC на каждое приложение.
  * Токен оболочки берётся только у **неповышенного** `explorer.exe`: если `TokenElevation` показывает, что оболочка сама повышена (UAC выключен, пользователь в группе Administrators), деэлевация невозможна — `restore` пишет об этом в отчёт, а не поднимает всё администраторским молча (`ShellToken`, `OpenShellToken` в `launcher.cpp`).
  * `CreateProcessAsUser` требует привилегий `SeIncreaseQuota` и `SeAssignPrimaryToken` — `EnablePrivilege` включает их у нашего токена; если политика не даёт, `RunAsDesktopUser` откатывается на `CreateProcessWithTokenW` (`SeImpersonate`), а при отказе и там — честная ошибка в отчёте и строка в `admin.log`. Окружение берётся у пользователя (`CreateEnvironmentBlock`/`userenv.lib`), рабочий стол — `winsta0\default`: иначе процесс получает окружение администратора и невидимый рабочий стол.
  * Права видны в отчёте: «запускаю: … (как пользователь)» и в `--dry-run` — суффикс «(как пользователь)» у плана.
* Все такие случаи пишем в `admin.log` рядом с exe, и формат у него с 0.8.3 самый практичный: **одна строка — одна готовая команда для `cmd.exe`** (CONTEXT п. 57). Ни заголовка, ни причины, ни имени десктопа в файле нет — их печатает консольный отчёт `restore`, а журнал нужен для того, чтобы строку можно было скопировать в консоль и получить окно на нужном столе:
  ```
  "C:\Program Files\OpenConnect-GUI\openconnect-gui.exe"
  "C:\Windows\SYSWOW64\Taskmgr.exe"
  "C:\Program Files (x86)\Google\Chrome\Application\chrome.exe" "https://ikrut.pro/Water2/"
  ```
  Переводы строк и `|` внутри полей не проблема: команда схлопывается в одну строку (`OneLine`). Если команду собрать не из чего (пустой `exe`), строка не пишется вовсе — в журнале остаются только осмысленные записи. Метки времени нет: файл описывает **только последний запуск** `restore`, поэтому время ничего не различает. `move-desktop-failed` с 0.8.1 означает, что не сработали **оба** пути переноса (внутренний и документированный) и окно после трёх попыток осталось на прежнем десктопе — раньше эта строка появлялась на любом чужом окне из-за `E_ACCESSDENIED` документированного API.
* `admin.log` **перезаписывается при каждом `restore`**, а не дополняется. Если за запуск записей не появилось, старый файл удаляется — иначе он выглядит как свежий отчёт. Ротация (`admin.old.log`) больше не нужна: файл всегда содержит одну сессию.
* В конце работы: если записи есть — открываем файл в `notepad.exe` (`ShellExecuteW(..., L"open", L"notepad.exe", adminLogPath, ...)`), чтобы пользователь сразу увидел, что нужно поднять руками. Окно блокнота с `admin.log` от прошлого запуска перед этим закрывается (`WM_CLOSE` для окон класса `Notepad` с `admin.log` в заголовке): иначе окна копятся на экране, а старое окно показывает прошлую сессию (блокнот не перечитывает файл). Если записей нет — ничего не открываем.
* Файл пишется в UTF-8 **с BOM** (иначе блокнот принимает UTF-8 за ANSI и кириллица превращается в мусор). Строки копятся в памяти и пишутся одним куском в `WriteAdminLog` — недописанных и перемешанных с прошлым содержимым файлов не бывает.

> Реализовано на этапе 7 (0.7.0), переработано на этапе 8 (0.8.0) и ещё раз на этапе 8.3 (0.8.3): `src\admin_log.cpp/.h`. В 0.8.3 `AddAdminEntry(reason, command)` получает **готовую команду** (`launcher.cpp`: `AdminCommand(window)` — exe + параметры: адрес страницы у браузера, папка у Проводника, аргументы из `cmdline` у остальных), а причины (`move-blocked`, `move-desktop-failed`, `launch-elevation-required`, `launch-failed`, `launch-timeout`, `console`, `browser-no-url`, `no-command`) остаются только в консольном отчёте и в `Trace`. Строка схлопывается в одну (`OneLine`), пустая команда не пишется (только `Trace`), ошибки записи не фатальны и уходят в отчёт. Строки накапливаются в памяти, `WriteAdminLog` пишет файл целиком (`CREATE_ALWAYS`, UTF-8 + BOM) и удаляет файл, если записей нет; `OpenAdminLogIfNeeded` закрывает прежние окна блокнота с `admin.log` и открывает файл заново. Проверено на этой машине: в 0.8.0 после `restore` в `admin.log` были две строки (`openconnect-gui.exe` и `Taskmgr.exe` — `move-blocked`), меток времени нет, кириллица читается, на экране одно окно «admin.log – Блокнот»; повторный прогон целиком заменяет содержимое, а не дописывает.

### 9.4 UWP и «специальные» окна

* `ApplicationFrameWindow` — координаты берём/ставим для frame-окна; AUMID из `P_AppUserModel_ID`.
* Cloaked-APP (suspended) окна часто не реагируют на перемещение — активируем через `IApplicationActivationManager` или пропускаем с пометкой `uwp-suspended`.
* Консольные окна (`ConsoleWindowClass`, ConEmu, Windows Terminal на Win10 — `CASCADIA_HOSTING_WINDOW_CLASS`) — обрабатываем как обычные окна. С перезапуском сложнее: в `cmdline` у них командная строка хоста, «как есть» её повторять нельзя, но и отказываться целиком неверно (CONTEXT п. 70). Правило с 0.9.3: если у хоста есть аргументы (`cmd.exe /c "term.bat"`, `powershell.exe -File …`) и сам хост существует — запускаем эту команду в **своей** консоли (`CREATE_NEW_CONSOLE`), и окно получает место как обычное; если аргументов нет (`cmd.exe`, `powershell.exe`) — не перезапускаем вовсе (пустая консоль бесполезна) и пишем строку в `admin.log` с причиной `console`.
* **Удалённый доступ (`mstsc.exe`, класс `TscShellContainerClass`)** — обычное окно: exe, геометрия, состояние и `cmdline` читаются, а `cmdline` ещё и запускабельная (`"mstsc.exe" "G:\...\сервер.rdp"`), т.к. пользователь стартует RDP из `.rdp`-файла. Служебные окна сеанса (`TSC_POPUP_PARENT_WNDCLASS`, `RdpClipRdrWindowClass`, `RDPSoundDVCWnd`, `{28181237-…}`, PAL-таймеры) невидимы и отсеиваются штатно.
* **Виртуальные машины (`VirtualBoxVM.exe`, менеджер `VirtualBox.exe`, класс `Qt653QWindowIcon`)** — тоже обычные окна, но с двумя оговорками:
  * `cmdline` у `VirtualBoxVM` — **внутренняя командная строка перезапуска** (`<uuid>-suplib-3rdchild --comment <имя> --startvm <GUID> …`), «как есть» она не запускается. Для фазы B (запуск) собирать команду заново: `VirtualBoxVM.exe --startvm <GUID>`; GUID брать из `--startvm` сохранённой строки (проверено на 7.1: `--startvm 4b1ccd45-1e72-4d34-9017-bd328f68ce9f`).
  * у развёрнутой ВМ `GetWindowRect` = весь монитор, а `rcNormalPosition` = то, каким окно было до разворота (на проверочной машине `-8,-8 656x562`) — сохранять и сравнивать надо `rcNormalPosition`, иначе после `restore` «нормальный» размер окна теряется.
  * полноэкранный режим ВМ (Host+F) — окно `WS_POPUP` без `WS_MAXIMIZE`, `rcNormalPosition` = монитор: от `max` программно не отличается, восстанавливается как `normal` на весь монитор — ожидаемое ограничение, помечаем в отчёте.

### 9.5 Иконки для ярлыков

Ярлыки создаёт пользователь, поэтому иконки должны быть доступны отдельно и вшиты в exe:

* `tools\make_icons.ps1` — генерирует `bin\save.ico` и `bin\restore.ico` (16/32/48/256 px) через `System.Drawing`: «save» — зелёная дискета со стрелкой вниз, «restore» — синее окно со стрелкой «развернуть обратно». Скрипт запускается один раз при сборке (лежит в репозитории, зависимостей не требует).
* `ScreenMemory.rc` — группы иконок `IDI_SAVE` (первая) и `IDI_RESTORE`; собирается `rc.exe` в `T:\ScreenMemory\obj\app.res` и линкуется в exe.
* Пользователь при создании ярлыка нажимает «Сменить значок» → выбирает `ScreenMemory.exe` → в списке видны 2 иконки (сохранить / восстановить) по индексам.
* Заодно `save.ico`/`restore.ico` остаются рядом с exe — можно указать их напрямую, если так удобнее.

## 10. Командная строка

```
ScreenMemory.exe save         # снять слепок текущей раскладки
ScreenMemory.exe restore      # восстановить раскладку из layout.txt
ScreenMemory.exe restore --from <файл>   # восстановить из другого слепка (0.9.1)
ScreenMemory.exe AutoSave     # поставить в Планировщик сохранение каждые N минут (0.9.0)
ScreenMemory.exe AutoRestore  # поставить в Планировщик восстановление при входе (0.9.0)
ScreenMemory.exe Uninstall    # снять задачи AutoSave/AutoRestore и автозагрузку (0.9.0)
```

* `--from <файл>` (0.9.1) — у `restore`: имя ищется рядом с exe, абсолютный путь берётся как
  есть. Это откат на рабочую версию, «вчерашний день» или «прежнюю конфигурацию» без
  переименований (§6.1); «цепочка дней» в этом случае не двигается, потому что откат — не
  начало нового дня. С другими командами ключ — ошибка разбора (код 64).

* Запуск — ровно одна команда (уточнение пользователя 15.11.2026): `save restore`, `AutoSave --list`,
  `--list --version` — ошибка разбора, справка + код 64. Без параметра — краткая справка в консоли
  (код 0). `AutoSave`/`AutoRestore`/`Uninstall` требуют прав администратора (без них код 5), их
  устройство — в §11.
* Консольная подсистема; запуск двойным щелчком по ярлыку, окно консоли закрывается по нажатию клавиши в конце (чтобы успеть прочитать отчёт).
* Скрытые отладочные ключи (нужны мне при разработке; обычному запуску не мешают, перед финалом можем убрать):
  * `--verbose` — подробный лог каждого шага в консоль и в `T:\ScreenMemory\screenmemory.log`: какие окна отброшены фильтром и почему, cloaked-флаги, результат матчинга с баллами, rect до/после применения, коды ошибок WinAPI. Без него печатается только краткий итог.
  * `--list` — ничего не сохраняет и не меняет: печатает текущие десктопы (индекс, GUID, имя, пометка «текущий»), pinned-приложения из реестра и все окна с колонками `hwnd | pid | exe | class | title | rect | show | cloaked | desktop`; плюс, если есть `layout.txt`, карту «десктоп из файла → десктоп сейчас» с пометками `renamed`/`ambiguous-name`/`fallback`. Основной инструмент проверки на этапах 2–4 и самый безопасный способ проверить сопоставление десктопов перед `restore`.
  * `--dry-run` — у `restore`: делает всё то же (читает файл, строит карту десктопов, матчит окна, планирует запуск), но **не** применяет геометрию, никуда не переносит окна и ничего не запускает; печатает план «что было бы сделано» и прогноз проблем. У `AutoSave`/`AutoRestore`/`Uninstall`: печатает XML задачи (или что найдено для удаления) и ничего не регистрирует и не удаляет.
  * `--hidden` (0.9.0) — скрыть окно консоли и не ждать клавишу; так программу запускают задачи Планировщика. При `--hidden` лог-файл ведётся всегда, иначе ошибка фонового запуска пропала бы молча.

## 11. Автозапуск: команды `AutoSave`, `AutoRestore`, `Uninstall`

Автозапуск — не «по умолчанию», а по желанию пользователя: три отдельные команды (уточнение
пользователя 15.11.2026). Всё через Планировщик заданий, от имени текущего пользователя
(задачи создаются без пароля, чтобы не спрашивать его каждые 10 минут).

* Права: задачи регистрируются с `<RunLevel>LeastPrivilege</RunLevel>` и
  `<LogonType>InteractiveToken</LogonType>` (`src\scheduler.cpp`: `BuildTaskXml`) — админ
  нужен только на регистрацию и снятие задач (`RequireElevation` в `main.cpp`), а сами
  прогоны `save --hidden`/`restore --hidden` идут с обычным токеном. Поэтому автозапуск
  не превращает восстановленные приложения в администраторские (PLAN.md §9.3, README
  «UAC при каждом запуске»): что требует повышения — попадает в `admin.log`.
* `ScreenMemory.exe AutoSave` — задача `ScreenMemory AutoSave`: «каждый день, повторять
  каждые N минут», команда — `"<exe>" save --hidden`. Интервал — ключ `AutoSave` в
  `Config.ini`, минуты, по умолчанию 10, зажимается в 1…1440.
* `ScreenMemory.exe AutoRestore` — задача `ScreenMemory AutoRestore`: триггер «При входе в
  систему» + задержка, команда — `"<exe>" restore --hidden`. Задержка — ключ
  `AutoRestoreDelay`, секунды, по умолчанию 30 (0 — без задержки), максимум 3600. Задержка
  нужна, чтобы приложения из автозагрузки успели открыть окна сами: `restore` только
  расставит уже существующие окна и поднимет недостающие, поэтому «кто первый» влияет на
  то, что попадёт в матчинг.
* `ScreenMemory.exe Uninstall` — снимает обе задачи и, на всякий случай, значение
  `ScreenMemory` из `HKCU\...\CurrentVersion\Run` (если автозагрузка когда-то ставилась
  вручную).

Правила для всех трёх:

* **Нужны права администратора.** Задачи Планировщика и их удаление Windows разрешает менять
  только с повышенными правами; без них печатается объяснение и код возврата `5`
  (у `save`/`restore`/`--list` прав по-прежнему не требуется). Уточнение по факту: без прав
  отказывает именно **триггер «при входе в систему»** (это же подтверждает `schtasks /Create
  /SC ONLOGON`; тот же XML с заменой триггера на обычное расписание регистрируется без
  повышения), а `AutoSave` Планировщик принимает и без него. Требование прав оставлено для всех
  трёх команд сознательно: `Uninstall` снимает в том числе задачу входа, и «одна команда — одни
  права» понятнее пользователю, чем «эта работает, эта нет».
* **Ключи взаимоисключающие**: одна команда за запуск. Сочетания (`save restore`,
  `AutoSave restore`, `--list --version`, `AutoSave --list`) — ошибка разбора, код `64`,
  с прямым текстом, что именно не так.
* `--dry-run` вместе с этими командами ничего не меняет: печатает расписание и путь к XML
  задачи (его можно зарегистрировать вручную через `schtasks /Create /XML ...`) либо
  показывает, что найдено для удаления.
* `--hidden` прячет окно консоли и отключает ожидание клавиши — так программу запускают
  задачи; при `--hidden` лог-файл ведётся всегда (`T:\ScreenMemory\screenmemory.log`), иначе
  ошибка фонового запуска пропала бы молча.
* **XML задач проверяется без прав:** `powershell -File tools\check_task_xml.ps1` читает оба
  файла из `%TEMP%` (их пишет `--dry-run`) и сверяет BOM, схему, SID, `InteractiveToken`,
  `IgnoreNew`, лимит времени, триггер (интервал/задержка — из `Config.ini`), команду и рабочую
  папку; `-Register` дополнительно регистрирует копию под временным именем и сразу снимает её
  (для `AutoRestore` — с заменой триггера входа на обычное расписание, потому что без прав
  отказывает только он). Так проверено, что Планировщик принимает оба XML: `AutoSave` — как
  есть, `AutoRestore` — во всём, кроме триггера.

Ручной вызов `save` перед перезагрузкой по-прежнему полезен: `AutoSave` раз в 10 минут может
не успеть записать последние изменения.

**Почему `AutoSave` почти не изнашивает диск.** Задача срабатывает часто, но `save` теперь
сравнивает собранный слепок с тем, что уже лежит в `layout.txt` (`SameLayoutContent`), и при
совпадении не пишет файл вообще — ни `layout.txt`, ни ротацию. Сравниваются десктопы (GUID,
имя, порядок), мониторы (границы, рабочая область, DPI, основной), экран и окна (десктоп,
exe, cmdline, url, класс, папка, заголовок, AUMID, монитор, `mrel`, `rect`, `frame`, `show`,
`uwp`) — как множество, без учёта порядка записей. Не сравниваются: `zg` (z-order меняется от
каждого клика по окну — переписывать из-за него файл бессмысленно) и строка `# saved=`.
Строковые значения сравниваются после `Trim` — ровно так их читает парсер; иначе пробел в
конце `cmdline` делал слепок «вечно изменившимся» (на этой машине так и было: окно
`HTTPserver`, `cmdline` с хвостовым пробелом). Причина отличия печатается в `--verbose`
(`LayoutDiffReason`): «окно «…»: новое», «монитор …: другие границы» и т. п.

## 13. Тестовый сценарий (ручной, на этой машине)

### 13.0 Полигон: как тестировать, не теряя текущую раскладку

Постоянные тестовые десктопы `Test1…TestN` **не нужны** — они мешают: слепок начнёт врать про реальную картину, а индексы десктопов будут плавать от теста к тесту. Нужны только временные, под конкретную проверку.

Правила безопасного тестирования:

1. Перед любыми экспериментами — `ScreenMemory.exe save`. Тогда всегда есть `layout.txt`, рабочие версии (по умолчанию 3, число задаёт ключ `Layouts`) и защищённые копии, откуда можно вернуться без переименований: `ScreenMemory.exe restore --from <файл>`.
2. **Окна для теста** — на уже существующих десктопах: 2–3 Блокнота и 2 окна Проводника на разные папки (`C:\Windows`, `T:\ScreenMemory`), расставленные характерно: на левом мониторе, на правом, окно через границу мониторов, одно свёрнутое, одно развёрнутое. Это покрывает 95 % логики (позиция, размер, состояние, монитор-якорь, clamp).
3. **Временный тестовый десктоп** — только когда проверяем «лишние десктопы»: перейти на десктоп 0, `Ctrl+Win+D` (новый создаётся справа от текущего), переименовать в `Test1`, открыть там Блокнот, `save`, `restore`, затем удалить десктоп. Реальные окна при этом не двигаются.
4. **Удаление десктопа** — только заведомо пустого/тестового. Если на десктопе есть окна, Windows перенесёт их на соседний: окна не теряются, но их десктоп изменится, и `restore` вернёт их по GUID.
5. Создание временного десктопа посреди списка сдвигает индексы — это как раз то, что программа обязана переживать (матчинг по GUID), так что такой тест полезен.
6. Реальные `Работа`/`Game`/… в тестах не переименовываем. Переименование проверяем на `Test1`: создать → `save` → переименовать в `Test2` → `restore` → окна вернулись на него же (по GUID).

Итог: постоянные `TestN` не заводим; для тренировки достаточно пары окон Блокнота на разных десктопах и одного временного десктопа, который создаём и удаляем внутри теста. Все деструктивные шаги — только после `save`.

### 13.1 Порядок ручных проверок

1. `list` → сверить индексы/имена с Task View (пример: `0 Работа` … `3 ESP32`); затем **переименовать** один десктоп и убедиться, что `list` показывает новое имя — значит имена читаются из реестра, а не из кода.
2. Открыть: 2 окна на первом десктопе, 1 на третьем, по окну Проводника на двух разных десктопах (одна и та же папка), Telegram (pinned).
3. `save` → открыть `bin\layout.txt`: все окна + pinned, у всех заполнены `desktop`/`desktop_name`/`monitor`/`mrel`, у Проводника верные `folder`, секции `[monitor.N]` соответствуют реальным мониторам.
4. Подвигать/свернуть/перетащить окна на другие десктопы → `restore` → всё вернулось.
5. Закрыть окна Проводника и Telegram → `restore` → запустились по одному разу, дублей нет.
6. **Переименовать десктоп** (например `Game` → `Игры`) → `restore` → окна вернулись на него же (матч по GUID), в отчёте `renamed`.
7. **Добавить новый десктоп** → `save` пишет его в файл, `restore` не съезжает с прежних десктопов.
8. **Удалить десктоп**, на котором были окна → `restore --dry-run` показывает `fallback`; реальный `restore` → окна на десктопе 0 в тех же координатах.
9. **Десктоп без имени** (убрать `Name` в реестре) → `save` пишет `name=` пустым, `restore` находит по GUID.
10. **Оставить один десктоп** → `save`/`restore` работают без ошибок (в файле одна секция `[desktop.0]`).
11. Сделать 7 `save` подряд → остаётся `Layouts` (по умолчанию 3) файлов `layout-*.txt` + текущий; откат — `restore --from layout-<время>.txt` (переименования не нужны).
12. Перезагрузка → `restore` → сравнить с п. 3 (главный тест).
13. **Браузер с восстановлением сессии** (Firefox): закрыть все окна Firefox → `restore --verbose` → на столе ровно одно новое окно с одной вкладкой сохранённого адреса, окно восстановленной сессии остаётся на текущем столе, пустого окна «Новая вкладка» нет; повторить 3 раза — копии адреса не прибавляются.
14. **Телевизор на втором мониторе** (`Config.ini`, ключ `prelaunch`): настоящий `restore` сначала поднимает `MultiMonitorTool.exe` и ждёт, пока её окно не закроют; пока окно открыто, восстановление не начинается; после закрытия — обычный отчёт (и раскладка уже считается по «настоящему» второму монитору). `save` предварительный шаг не выполняет (он только записывает то, что видно). Отдельно проверить отказы: `prelaunch-timeout=2` при незакрытом окне → предупреждение и продолжение; путь в никуда → «программы нет» и продолжение; `--dry-run` и `--list` предварительный шаг не выполняют.

## 14. Риски и ограничения (осознанные)

1. **Гарантий, что Windows 10 сохранит те же десктопы (количество, имена, GUID) после перезагрузки, нет.** Митигация: матчинг GUID → имя → индекс, при провале — первый десктоп (требования 7, 8, 15). Программа не завязана ни на число десктопов, ни на их имена.
2. Окна, которые приложение само расставляет при старте, могут «дёрнуться» — компенсируем ретраем через 2 с.
3. Часть приложений сопротивляется внешнему позиционированию (игры/fullscreen, некоторые Electron с кастомным frame) — best-effort, попадёт в отчёт.
4. Elevated-приложения требуют запуска от админа — сознательно не включаем по умолчанию (п. 9.3).
5. `PinnedApps` — не официально документированный ключ. Если он изменится, pinned-детект деградирует: окна восстановятся по одному на конкретный десктоп, без размножения (безопасный фолбэк).
6. Разный DPI на мониторах: работаем в физических пикселях (PerMonitorV2), поэтому окно, переехавшее между мониторами с разным масштабом, может изменить размер на несколько пикселей.
7. Мы не храним содержимое приложений (вкладки браузера, открытые документы) — только окна, позиции и папки. Приложения без собственного восстановления состояния откроются «как новые».
8. Окна, созданные через `CreateProcess` с прямым путём к exe, но реально принадлежащие другому процессу (лаунчеры, Chrome), матчатся по class+title, а не по PID — возможны осечки, отсюда ретраи и отчёт.
9. Браузер, который восстанавливает сессию профиля (Firefox), сам открывает окно сессии — `restore` его не закрывает и не переносит, потому что в нём вкладки пользователя. При холодном старте это окно останется на том столе, который был активным, а новое окно с сохранённым адресом встанет на своё место (CONTEXT п. 63).
10. **Предварительный шаг ждёт пользователя.** Если задан `prelaunch`, `restore` не начинает работу, пока не закроют окно программы, — при автозапуске из Планировщика задача завершится только после этого. `prelaunch-timeout` ограничивает ожидание (работа продолжится, но раскладка второго монитора может быть ещё «не той»). `save` шаг не выполняет. Саму программу мониторов ScreenMemory не настраивает: она только запускает её с необязательными `prelaunch-args` и ждёт закрытия окна.

## 15. Принятые решения (зафиксировано с пользователем)

1. **Один exe** `ScreenMemory.exe` с параметрами `save` / `restore` — и всё. Никаких других команд.
2. **Консольное** приложение; запуск вручную через два ярлыка на рабочем столе с понятными иконками. Иконки генерируем сами (см. 9.5) и вшиваем в exe.
3. Файлы раскладки — в той же папке, что и `ScreenMemory.exe` (папку пользователь выберет сам, программа портативна). Во время разработки — `bin\`.
4. **Отсутствующие приложения запускаем**: ждём появления окна, затем позиционируем/меняем размер/переносим на нужный десктоп.
5. **Десктопы программой не создаются.** Если нужного десктопа нет — окно идёт на нулевой (первый) десктоп в тех же координатах.
6. `pinned`-окна — один экземпляр, между десктопами не переносим.
7. **Никаких запусков от администратора.** Всё, что требует админа, пишем в `admin.log` и открываем его в блокноте перед завершением.
8. Координаты — **относительные от угла монитора** (монитор-якорь + `mrel`), абсолютные `rect` — только для сверки.
9. Рабочих версий `layout.txt` хранится `Layouts` (по умолчанию 3, допустимо 1…20), откат — `restore --from <файл>`; рядом неприкосновенные копии «вчерашний день» и «прежняя конфигурация» (§6.1).
10. Окна на других виртуальных десктопах обязательно попадают в слепок (через DWM-признак cloaked, см. 9.0).
11. Имена и количество виртуальных десктопов **не захардкожены**: `save` берёт всё, что есть (1…N), `restore` сопоставляет по GUID → имени → индексу. Переименование, добавление, перестановка и удаление десктопов не ломают восстановление.
12. «Нулевой десктоп» = первый в текущем порядке, а не десктоп с именем «Работа».
13. **Кодировки зафиксированы**: C++-исходники — UTF-8 (сборка с `/utf-8`), bat-файлы и PowerShell-скрипты — только ASCII. Это не стилистика, а лечение реальных грабель: `cmd.exe` ломает UTF-8 в bat, а Windows PowerShell 5.1 без BOM читает `.ps1` как ANSI.
14. **Коды возврата** зафиксированы в контракте: `0` — успех, `1` — восстановлено не всё (ошибки применения/запуска, окна уехали на десктоп 0 из-за отсутствующих десктопов либо в `admin.log` появились записи — окно осталось за человеком), `2` — нет файла раскладки или он битый, `3` — не удалось получить список десктопов, `5` — `AutoSave`/`AutoRestore`/`Uninstall` запущены без прав администратора, `6` — переносы окон между десктопами невозможны на этой сборке Windows, `64` — неверная командная строка. `save`/`restore` печатают краткий отчёт; при запуске двойным щелчком (консоль создана только для нас) в конце ждём нажатия клавиши — `GetConsoleProcessList` возвращает 1 (с `--hidden` не ждём — так программу запускают задачи).
15. **Иконки** генерируются `tools\make_icons.ps1` в `bin\save.ico` и `bin\restore.ico`: 16/32/48 px — BMP-записи внутри ICO, 256 px — PNG-запись. Порядок ресурсов задаёт иконку exe по умолчанию: `IDI_SAVE` (101) первая, `IDI_RESTORE` (102) вторая. Внутри PowerShell нельзя возвращать `byte[]` без унарной запятой (`return , $arr`) — иначе массив разворачивается и ICO получается битым (проверено `rc.exe`: `RC2176 old DIB`).
16. **COM закрываем последним.** `sm::UninitCom()` вызывается в `wmain` уже после того, как команда вернула управление и все локальные объекты (в том числе `IVirtualDesktopManager`) разрушены. Если отпустить интерфейс после `CoUninitialize()`, процесс падает с `0xC0000005` — поймано на `tests\smoke.bat` (команда `--list`), лечится только порядком вызовов.
17. **`data` в `PinnedApps` — всегда 0**, поэтому «закреплено» определяем по факту наличия значения в ключе, а не по его данным (`data` пишем только в `--verbose` для диагностики).
18. **Текущий десктоп определяется каскадом, а не одним вызовом.** Порядок: окно в фокусе (`GetForegroundWindow` + `GA_ROOTOWNER`/`GA_ROOT`) → `GetConsoleWindow` → голосование по окнам (`EnumWindows`: только видимые и не cloaked по `DWMWA_CLOAKED`, плюс `IsWindowOnCurrentVirtualDesktop`; побеждает десктоп с большинством окон, при равенстве — самое верхнее окно) → окна оболочки (Progman, `Shell_TrayWnd`, `Shell_SecondaryTrayWnd`) → значение `CurrentVirtualDesktop` в реестре. Причина: под ConEmu `GetWindowDesktopId` для окна `VirtualConsoleClass` возвращает `0x8002802B` (`TYPE_E_ELEMENTNOTFOUND`), и одиночная попытка давала «текущий десктоп не определён». В `--verbose` печатается строка `диагностика десктопа: фокус=…, консоль=…, голосование=…, оболочка=…, реестр=…` — результат каждого способа; на этой машине фокус и голосование (35 из 35 окон) совпадают, а 2 «кандидата» в голосовании — это pinned-окна, видимые на всех десктопах.
19. **Pinned-окна выдают GUID, которого нет в списке десктопов.** Все 6 pinned-окон этой машины (Telegram, VSCode, OpenConnect, taskmgr, Часики, AudioPL) возвращают один и тот же `{BB64D5B7-4DE3-4AB2-A87C-DB7601AEA7DC}`, причём такого ключа нет в `HKCU\...\VirtualDesktops\Desktops` — это маркер «показывать на всех рабочих столах», а не десктоп. Поэтому `DetectCurrentDesktop(..., knownDesktops)` при голосовании **игнорирует GUID, которых нет в текущем списке** (`--verbose`: `голосование по окнам: видимых 38, с десктопом 29 (не из списка 6), на текущем 23, кандидатов 1`). Без фильтра на десктопе, где окон меньше, чем pinned-приложений, голосование выбирало бы маркер и «текущим» становился несуществующий десктоп. В `--list` такие окна выводятся отдельной группой с явной пометкой.
20. **Пустые UWP-рамки отбрасываются.** `ApplicationFrameWindow` без заголовка принимается только при наличии внутри `Windows.UI.Core.CoreWindow`; рамка без содержимого — пустышка (`pid` = `explorer.exe`, дети только `ApplicationFrameTitleBarWindow`/`ApplicationFrameInputSinkWindow`, размер = монитор). Именно такие две рамки давали в `--list` группу «десктоп не определён»: у них к тому же нет записи в диспетчере десктопов. Заголовок UWP-окна, если он пуст на рамке, читается из дочернего `CoreWindow`.
